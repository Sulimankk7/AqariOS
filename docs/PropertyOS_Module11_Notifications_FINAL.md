# MODULE 11 — NOTIFICATIONS

Continuation of `PropertyOS_Phase3_Physical_Design.md`, `PropertyOS_Module4_Properties.md`, `PropertyOS_Module5_Leasing.md`, `PropertyOS_Module6_RentPayments_Updated.md`, `PropertyOS_Module7_FinancialOperations_Updated.md`, `PropertyOS_Module8_Maintenance.md`, `PropertyOS_Module9_Marketplace.md`, and `PropertyOS_Module10_Documents.md`. Applies the same Global Conventions (UUIDv7 PKs, `created_at`/`updated_at`/`created_by`/`updated_by`, soft delete, `company_id` + RLS tenant isolation, `snake_case` naming) unless a deviation is explicitly justified.

Scope for this module is deliberately narrow, per the module brief: **three tables only** — `notification_templates`, `notifications`, `notification_deliveries`. No push-provider integration tables, background-job/queue tables, campaign/marketing-notification tables, scheduling-engine tables, subscription/opt-in-preference tables, or any new notification concept beyond what is named — those are explicitly out of scope and are not introduced anywhere below, even implicitly via a stray column.

Scale target for this module: **10,000+ companies, 50,000,000+ notifications, 150,000,000+ notification delivery records.**

## 11.0 Module-Wide Design Decisions (read before the tables)

**This module narrows Phase 1 §1.27's conceptual `notifications` design to a single, mandatory recipient — `recipient_user_id` — not the dual-nullable `user_id`/`tenant_id` shape originally sketched, and not the "weak relationship" pattern Phase 2 §2.4 (item 2) already flagged and recommended a CHECK constraint for.** Phase 1's conceptual description allowed a notification's recipient to be either a `users` row or a `tenants` row, since a tenant without portal access still needs to receive SMS/WhatsApp payment reminders. This module's explicit brief — "Company, Recipient User, Template (optional), Notification Type, Subject, Body, Status, Priority, Read At, Created At" — names only a single, mandatory `Recipient User` field, with no `tenant_id` counterpart. This is a deliberate scope decision matching the stated field list, not an oversight, and it has a real structural consequence worth flagging explicitly: per Phase 1 §1.9, a `tenants` row carries an *optional* `user_id` link, populated only once/if a tenant activates portal access. Under this module's narrowed, single-FK design, **a tenant who has never activated portal access has no `users` row to be a `recipient_user_id` for**, and therefore cannot be the direct recipient of a row in this table as currently scoped. This is documented here so it is not silently forgotten: a future pass reintroducing tenant-without-portal notification delivery (e.g., SMS/WhatsApp-only reminders) is a clean additive extension — either a nullable `tenant_id` column added alongside a CHECK constraint enforcing exactly one of `recipient_user_id`/`tenant_id` non-NULL (the Phase 2 §2.4-recommended shape), or a sibling table — not a redesign of the columns and constraints already built here for the in-scope case. Every table in this module remains internally consistent and fully correct for its stated scope; this note exists purely so the boundary is visible rather than discovered later.

**`notification_templates` mirrors `document_categories`' company-scoped-table-with-seeded-defaults pattern (Module 10 §10.0), not the `roles`-style system/custom split.** The module brief lists ten specific, named template types ("New Lease," "Lease Expiration," "Rent Due," "Rent Paid," "Late Payment," "Maintenance Request Created," "Maintenance Request Updated," "Marketplace Viewing Request," "Document Expiring," "General Notification") and states "Templates are managed per company." Consistent with the identical reasoning already applied to `document_categories` (Module 10 §10.1) and, before that, `notification_templates` itself in Phase 1 §1.28 ("Company-scoped with system-default fallback templates seeded per event type, so a new company works out of the box"), every `notification_templates` row — including the ten seeded defaults — is a genuine company-scoped row (`company_id NOT NULL`), seeded into a new company's own rows at signup via the same application-orchestrated transaction pattern already established for `company_settings` (Module 1 §1.2), `company_receipt_sequences` (Module 7 §7.4), and `document_categories` (Module 10 §10.1). `notification_type` is a closed, platform-defined enum (the ten stated values are exhaustive and structurally meaningful — application code branches on notification type to select which event triggers which template), whereas `template_name` remains free text so a company can maintain multiple named variants per type (e.g., an Arabic-toned and an English-toned "Rent Due" template, or a firmer-worded "Late Payment — Second Notice" variant) without the schema needing to anticipate every wording variation a company might want.

**`notifications` is the single logical record of "this event happened and this message was generated"; `notification_deliveries` is the record of "this message was attempted across this specific channel."** This is the direct structural analogue of the `rent_payments`/`payment_allocations` obligation-vs-settlement split (Module 6 §6.0) and the `maintenance_requests`/`maintenance_status_history` current-state-vs-history split (Module 8 §8.0), applied here to a one-notification-many-channels shape instead: a single logical notification (e.g., "rent due reminder for tenant X, apartment Y") is created once, but may be simultaneously pushed out over email, SMS, WhatsApp, and in-app — each with its own independent delivery lifecycle, retry count, and failure mode, none of which should mutate or multiply the parent notification's own single logical identity. Collapsing delivery-channel detail onto the `notifications` row itself (e.g., four sets of per-channel status columns) would violate 3NF for an unbounded-in-principle channel set and would make "how many channels has this notification been attempted on" an application-computed fact instead of a directly queryable one; splitting them, as done here, is the same 1:many-with-business-meaningful-child-attributes pattern already applied consistently since Phase 2 §2.1's M:M/1:many note.

**`notifications` immutability is content-immutability, not row-immutability — a deliberate, narrower rule than `meter_readings`/`login_history`'s full append-only treatment.** Per the stated business rule "Notifications are immutable after being sent," the row's message content (`subject`, `body`, `notification_type`, `recipient_user_id`, `template_id`) becomes fixed once `status` transitions to `sent` — this is the same guarantee `lease_contracts` gives its financial-term columns once `superseded` (Module 5 §5.1): immutability of *specific columns*, application-enforced, not a whole-row-never-updated rule. Two columns remain legitimately mutable after `sent`: `read_at` (per the stated rule "Reading a notification updates only ReadAt") and `status` itself (which must still be able to transition into `failed`/`cancelled` from certain states, and is the column the "immutable after sent" rule is itself gating). This is a narrower, more surgical immutability rule than the pure never-`UPDATE` event-log pattern used for `meter_readings`/`login_history`/`contract_status_history`, and is documented as such rather than mechanically reapplying the stricter pattern where it doesn't fit — `notifications` genuinely needs a small number of post-creation field updates (`status`, `read_at`) that an append-only design would force into an awkward multi-row model for no benefit.

**Denormalized `company_id` on every table in this module**, consistent with the module-wide denormalization principle established since Module 4 §4.0 and carried through every subsequent module — `notification_deliveries` carries `company_id` directly (denormalized from `notifications.company_id` at write time) so that company-scoped delivery-health dashboards and RLS policy evaluation on this module's child table never require a join through `notifications` just to establish tenant scope, identical reasoning to `listing_images`/`viewing_requests` carrying `company_id` denormalized from `marketplace_listings` (Module 9 §9.0).

**No soft delete on `notification_deliveries` — a deliberate, explicitly-justified deviation from the Global Convention, distinct in kind from `meter_readings`'/`login_history`'s deviation.** Per the stated business rule "Delivery history must never be deleted," this table carries no `deleted_at`/`deleted_by` columns at all. Unlike `meter_readings`/`login_history` (immutable, append-only, corrections are always additive new rows), `notification_deliveries` rows **are** legitimately mutable in place (`delivery_status`, `attempt_count`, `sent_at`, `delivered_at`, `failure_reason` all update as a retry progresses) — so this is not the "pure event log" deviation class. It is instead the identical deviation class already used for `company_receipt_sequences` and `subscription_plans`-style "no independent retirement mechanism needed" tables, but for the opposite reason: those tables omit soft delete because a row's *entire lifecycle* is expressed through non-deletion state; `notification_deliveries` omits it because the stated business rule is an explicit, absolute retention mandate ("must never be deleted") that would make a `deleted_at` column actively misleading — its mere existence would imply deletion is a legitimate operation on this table, which the brief explicitly forecloses. A genuine data-entry error on this table (a delivery row created against the wrong `notification_id`/`delivery_channel` pairing, corrected before any real send attempt) is handled by an application-layer correction to the erroneous row's fields directly (this table's own unique constraint, §11.3, already prevents a second competing row for the same notification+channel from being created alongside it), not by a delete of any kind, soft or hard.

## 11.1 Table: `notification_templates`

**Purpose:** The company-scoped, reusable message template each `notifications` row optionally renders from — the classification and wording backbone behind every event-driven notification the platform sends.

**Business Description:** Represents one reusable message template for a company — e.g., "Rent Due — Standard," "Lease Expiration — 30 Day Notice," "Maintenance Request Created — Tenant Confirmation." Every company gets its own independent set of template rows, seeded with the ten stated notification types at signup and freely extensible/editable thereafter.

**Columns:**

| Column Name | PostgreSQL Data Type | Nullable | Default | Description |
|---|---|---|---|---|
| id | UUID | NO | uuid_generate_v7() | Primary key |
| company_id | UUID | NO | — | Owning company — every template row belongs to exactly one company (stated requirement: "Templates are managed per company") |
| template_name | VARCHAR(150) | NO | — | The template's display/management name, e.g. "Rent Due — Standard", "Late Payment — Second Notice" — free text, since a company may maintain multiple named variants per `notification_type` |
| notification_type | notification_type_enum | NO | — | `new_lease` \| `lease_expiration` \| `rent_due` \| `rent_paid` \| `late_payment` \| `maintenance_request_created` \| `maintenance_request_updated` \| `marketplace_viewing_request` \| `document_expiring` \| `general_notification` — the stated closed list of ten supported template categories |
| subject | VARCHAR(255) | NO | — | Template subject line/headline, supporting placeholder tokens (e.g. `{{tenant_name}}`, `{{amount_due}}`) resolved at render time by the application, mirroring the token pattern already established conceptually in Phase 1 §1.28 |
| body | TEXT | NO | — | The full template message body, same placeholder-token convention as `subject` |
| is_active | BOOLEAN | NO | true | Retires a template from the selection picker without deleting it — the stated "Is Active" field; distinct from soft delete, see Business Rules |
| created_at | TIMESTAMPTZ | NO | now() | — |
| updated_at | TIMESTAMPTZ | NO | now() | — |
| created_by | UUID | YES | NULL | NULL for the ten system-seeded default rows created by the signup transaction with no human actor |
| updated_by | UUID | YES | NULL | — |
| deleted_at | TIMESTAMPTZ | YES | NULL | Soft delete |
| deleted_by | UUID | YES | NULL | — |

**Primary Key:** `id`

**Foreign Keys:**
- `company_id` → `companies(id)` ON DELETE RESTRICT.
- `created_by`, `updated_by`, `deleted_by` → `users(id)` ON DELETE SET NULL.

**Unique Constraints:** `uq_notification_templates_company_name` on `(company_id, template_name)` WHERE `deleted_at IS NULL` — the direct implementation of the stated **"Prevent duplicate template names within the same company"** integrity requirement. Scoped to `company_id`, not global, since two different companies routinely and legitimately both maintain a template named "Rent Due — Standard" — the identical company-scoped-uniqueness reasoning already applied to `uq_document_categories_company_name` (Module 10 §10.1) and `uq_lease_contracts_company_contract_number` (Module 5 §5.1). Deliberately **not** scoped to `(company_id, notification_type)` — a company is explicitly permitted multiple templates per type (the "Rent Due — Standard" vs. "Rent Due — Friendly Reminder" case), so uniqueness on type alone would incorrectly block a real, wanted multi-template-per-type workflow. Partial on `deleted_at IS NULL` so a retired template's name can be reused by a new template later, the identical partial-unique pattern used consistently since Module 3.

**Check Constraints:**
- `chk_notification_templates_name_not_blank` — `length(btrim(template_name)) > 0` — mirrors `chk_document_categories_name_not_blank` (Module 10 §10.1) and the same class of constraint applied throughout this schema to every short display-name column.
- `chk_notification_templates_subject_not_blank` — `length(btrim(subject)) > 0` — the direct implementation of the stated **"Blank subjects"** integrity requirement at the template level; a whitespace-only subject line is a real, cheap-to-catch data-entry failure mode.
- `chk_notification_templates_body_not_blank` — `length(btrim(body)) > 0` — the direct implementation of the stated **"Blank message bodies"** integrity requirement at the template level.

**Indexes:**
- `idx_notification_templates_company_type` composite on `(company_id, notification_type)` WHERE `deleted_at IS NULL AND is_active = true` — the primary **template-selection lookup**: "which active template(s) should I use to render a Rent Due notification for company X" — evaluated every time an event-driven notification is generated, across every event type in the platform. `company_id` leads as the mandatory tenant-scoping equality filter; `notification_type` second as the near-universal secondary equality filter (the notification-generation code path always knows exactly which type it's rendering). Partial on `is_active = true` specifically — not just `deleted_at IS NULL` — because template *selection* for a new outbound notification only ever considers active templates; an inactive-but-not-deleted template remains visible in the company's template-management screen (which uses the base `uq_notification_templates_company_name`-backed listing, unfiltered on `is_active`) but should never be silently selected for a new send.
  - *Queries served:* `SELECT * FROM notification_templates WHERE company_id = $1 AND notification_type = $2 AND is_active = true AND deleted_at IS NULL` (the event-driven notification-generation code path's template lookup, evaluated on every single notification created platform-wide).
  - *Expected performance improvement:* turns the single highest-frequency query against this table — evaluated once per notification generated, i.e., proportional to the 50,000,000+ target on `notifications` itself — into a tight, targeted index range-scan bounded to one company's small handful of templates per type, rather than a sequential scan of the company's full template set filtered in application code.
  - *Why preferred over a standalone `company_id` index:* identical reasoning established since Module 3 — a composite serving both the equality filter and the immediately-following equality refinement in one structure is strictly better than a single-column index requiring a secondary filter step, and a company's full template-management listing (which does need every template, active or not) is already adequately served by the unique constraint's own backing composite on `(company_id, template_name)` without needing a third index.

**Deliberately omitted index:** no standalone `notification_type` index without `company_id` leading. "All templates of type X across every company" has no realistic product query — template management is always company-scoped, never a platform-wide cross-tenant listing (unlike the intentionally-cross-tenant `marketplace_listings`, Module 9) — so a `notification_type`-leading index would serve no stated access pattern and would violate the "avoid unnecessary indexes" discipline applied consistently since Module 3.

**Business Rules:** The ten stated notification-type templates are seeded into a new company's own rows in the same signup transaction that creates its `company_settings` row (application-orchestrated, mirroring the identical pattern already established for `document_categories`, Module 10 §10.1, and `company_receipt_sequences`, Module 7 §7.4) — so a company's template picker for every stated event type is never empty on day one. Companies may freely rename, edit, deactivate, or add templates beyond the seeded ten; `notification_type` itself is the one closed/platform-governed dimension (a company cannot invent an eleventh notification type, since application code must know how to trigger each type's generation event), while `template_name`, `subject`, and `body` are fully company-editable. `is_active = false` is the correct mechanism for "stop using this template for new sends without losing its edit history or breaking any `notifications`/`notification_deliveries` row that already rendered from it" — a template referenced by at least one historical `notifications.template_id` cannot be hard-deleted (enforced by the `RESTRICT` FK below) but may be deactivated or soft-deleted to retire it from the picker; notifications already generated from a since-retired template continue to display their own already-rendered `subject`/`body` (stored directly on the `notifications` row itself, §11.2) regardless of the template's current state, since a notification's own content is a permanent historical fact independent of its originating template's later edits.

**Soft Delete Strategy:** Standard — reserved for a company genuinely retiring a template it no longer wants offered anywhere, including the management screen; `is_active = false` is the lighter-weight, more common "stop offering for new sends but keep visible in management" mechanism, mirroring the identical `is_active`-vs-`deleted_at` two-tier retirement pattern already used for `apartments.is_active`/`deleted_at` (Module 4 §4.4) and `marketplace_listings`-adjacent `parking_spots.is_active` (Module 4 §4.5).

**Audit Requirements:** Standard `audit_logs` coverage; template creation, wording edits (`subject`/`body`), and `is_active`/soft-delete transitions are all logged — a wording change to a live template is a real operational event worth tracing (e.g., "who changed the Late Payment template's tone last month"), though at standard, not elevated, severity, since a template edit alone has no direct financial/legal consequence until an actual notification renders from it.

**Future Scalability Notes:** Trivially small at any scale — even generously assuming every one of 10,000+ companies defines the ten seeded defaults plus several custom variants per type, this table stays in the low hundreds of thousands of rows platform-wide, comfortably within single-table territory indefinitely, the identical conclusion already reached for `document_categories` (Module 10 §10.4) and `company_settings` (Module 1 §1.2). No partitioning or additional indexing concern at any realistic scale.

## 11.2 Table: `notifications`

**Purpose:** The single logical record of one generated notification — the central anchor entity of this module and the parent of every delivery-channel attempt below.

**Business Description:** Represents one notification generated by the platform for one recipient user: a rent-due reminder, a lease-expiration notice, a maintenance-status update, a marketplace viewing-request alert, a document-expiry warning, or a general company-initiated notice. Captures the rendered message content (a permanent snapshot, independent of any later edit to the originating template), its priority, and its own lifecycle from generation through send/failure/cancellation and eventual read.

**Columns:**

| Column Name | PostgreSQL Data Type | Nullable | Default | Description |
|---|---|---|---|---|
| id | UUID | NO | uuid_generate_v7() | Primary key |
| company_id | UUID | NO | — | Owning company (tenant-scope root) |
| recipient_user_id | UUID | NO | — | FK to `users` — the stated "Recipient User" field; mandatory per this module's explicit single-recipient scope, see §11.0 |
| template_id | UUID | YES | NULL | FK to `notification_templates` — the stated "Template (optional)" field; nullable since a `general_notification`-type or genuinely ad-hoc staff-composed notification may have no originating template at all |
| notification_type | notification_type_enum | NO | — | Same closed ten-value domain as `notification_templates.notification_type` — denormalized onto this row (rather than requiring a join through `template_id`, which may itself be NULL) so every notification is independently classifiable/filterable by type even when it wasn't rendered from a template |
| subject | VARCHAR(255) | NO | — | The stated "Subject" field — the actual rendered subject line for *this specific* notification (placeholder tokens already resolved, e.g. "Rent due: 350.000 JOD by March 1"), a permanent snapshot independent of the originating template's later edits |
| body | TEXT | NO | — | The stated "Body" field — the actual rendered message body for this specific notification, same snapshot-independence rationale as `subject` |
| status | notification_status_enum | NO | 'pending' | `pending` \| `sent` \| `failed` \| `cancelled` — the stated closed status list |
| priority | notification_priority_enum | NO | 'normal' | `low` \| `normal` \| `high` \| `critical` — the stated closed priority list |
| read_at | TIMESTAMPTZ | YES | NULL | The stated "Read At" field — NULL until the recipient opens/acknowledges the notification; the *only* column, alongside `status`, permitted to change after `status = 'sent'` (§11.0) |
| created_at | TIMESTAMPTZ | NO | now() | The stated "Created At" field |
| updated_at | TIMESTAMPTZ | NO | now() | — |
| created_by | UUID | YES | NULL | NULL for the overwhelming majority of rows, which are system/event-generated, not staff-composed; populated only for a manually staff-composed `general_notification` |
| updated_by | UUID | YES | NULL | — |
| deleted_at | TIMESTAMPTZ | YES | NULL | Soft delete — reserved narrowly per the stated business rules, see Soft Delete Strategy |
| deleted_by | UUID | YES | NULL | — |

**Primary Key:** `id`

**Foreign Keys:**
- `company_id` → `companies(id)` ON DELETE RESTRICT.
- `recipient_user_id` → `users(id)` ON DELETE RESTRICT — per the stated "orphan notification records" concern applied to this table's own primary relationship: a notification's historical value (audit/delivery-proof) does not evaporate if the recipient's account is later deactivated, and `users` rows are themselves only ever soft-deleted (Module 3 §3.1) in the ordinary case, so RESTRICT here matches how every other durable-history FK in this schema treats its primary subject (e.g., `rent_payments.tenant_id`, Module 6 §6.1).
- `template_id` → `notification_templates(id)` ON DELETE RESTRICT — a template referenced by any historical notification can never be hard-deleted out from under it, identical reasoning to `building_documents.category_id` → `document_categories` (Module 10 §10.2).
- `created_by`, `updated_by`, `deleted_by` → `users(id)` ON DELETE SET NULL.

**Unique Constraints:** None. A notification has no natural business key — two genuinely distinct notifications (even identical in type/subject/recipient, e.g. two separate "Rent Due" reminders sent a month apart, or even the same day due to a legitimate resend) are not duplicates, they are two real, distinct events — the identical "no natural key, no dedup constraint" reasoning already applied to `expenses` (Module 7 §7.1) and `maintenance_requests` (Module 8 §8.1).

**Check Constraints:**
- `chk_notifications_subject_not_blank` — `length(btrim(subject)) > 0` — the direct implementation of the stated **"Blank subjects"** integrity requirement at the notification level (distinct from, and in addition to, the identical constraint already enforced at the template level, §11.1 — a notification's own rendered subject must independently be non-blank even though its template's subject already was, since a broken placeholder-substitution could theoretically render an otherwise-valid template down to an empty string).
- `chk_notifications_body_not_blank` — `length(btrim(body)) > 0` — the direct implementation of the stated **"Blank message bodies"** integrity requirement at the notification level, same rationale as above.
- `chk_notifications_read_at_not_future` — `read_at IS NULL OR read_at <= now()` — the direct implementation of the stated **"Invalid read timestamps"** integrity requirement's core case: a notification cannot be recorded as read at a point in time that hasn't happened yet.
- `chk_notifications_read_at_after_created` — `read_at IS NULL OR read_at >= created_at` — the second half of the "Invalid read timestamps" requirement: a notification cannot logically be read before it was even generated.
- `chk_notifications_read_requires_sent` — `read_at IS NULL OR status = 'sent'` — a notification that was never successfully sent (`pending`/`failed`/`cancelled`) has nothing for the recipient to have actually read; this is the structural implementation of "invalid notification states" as it applies to the `read_at`/`status` relationship specifically — a `failed` notification showing a populated `read_at` would be a logical impossibility the database should reject, not silently store.

**Indexes:**
- `idx_notifications_recipient_created` composite on `(recipient_user_id, created_at DESC)` WHERE `deleted_at IS NULL` — **the** primary **User Notification History** query (stated requirement): "full notification history for this user, most-recent-first" — the notification center / inbox screen every authenticated user opens. `recipient_user_id` leads as the mandatory equality filter for this screen; `created_at DESC` trails so the common "newest first" access is a direct ordered index scan with no separate sort step, mirroring the identical composite-with-trailing-DESC pattern established throughout Modules 3–10.
  - *Queries served:* `SELECT * FROM notifications WHERE recipient_user_id = $1 AND deleted_at IS NULL ORDER BY created_at DESC LIMIT 50` (the notification-center screen, paginated) — evaluated on essentially every authenticated session that opens the notification bell/inbox.
  - *Expected improvement:* turns a filter-then-sort over a table headed toward 50,000,000+ rows into a single ordered index range-scan bounded to one user's own notification volume (typically hundreds to low thousands over an active account's life, not millions).
  - *Why preferred over a standalone `recipient_user_id` index:* identical reasoning established since Module 3 — a composite with the sort column embedded serves both the equality filter and the ordering in one structure, avoiding a separate sort step a plain single-column index would still require.
- `idx_notifications_recipient_unread` composite on `(recipient_user_id, created_at DESC)` WHERE `read_at IS NULL AND status = 'sent' AND deleted_at IS NULL` — a deliberately narrower, partial-on-read-state companion index purpose-built for the single highest-frequency screen named in the brief: **Unread Notifications** — the notification-bell badge count and the "unread only" inbox filter, evaluated on effectively every page load across the platform (the badge count is typically fetched alongside session bootstrap). This mirrors the exact `idx_maintenance_requests_company_open_priority` (Module 8 §8.1) / `idx_viewing_requests_company_pending` (Module 9 §9.3) pattern of a narrow, single-purpose partial index reserved for the one query that matters most operationally.
  - *Queries served:* `SELECT COUNT(*) FROM notifications WHERE recipient_user_id = $1 AND read_at IS NULL AND status = 'sent' AND deleted_at IS NULL` (badge count); `SELECT * FROM notifications WHERE recipient_user_id = $1 AND read_at IS NULL AND status = 'sent' AND deleted_at IS NULL ORDER BY created_at DESC` (unread-filtered inbox view).
  - *Expected improvement:* because this index only ever contains currently-unread rows (a small, bounded fraction of a user's total historical notification volume at any given time — most notifications eventually get read and drop out of this partial index's row set), it stays small and fast indefinitely regardless of how large the table's full historical row count grows, the identical durability argument already made for `idx_rent_payments_late_overdue` (Module 6 §6.1) and `idx_building_documents_expiring` (Module 10 §10.2).
- `idx_notifications_company_status_created` composite on `(company_id, status, created_at DESC)` WHERE `deleted_at IS NULL` — the primary **Dashboard Statistics** query shape: "how many notifications failed/pending/sent for company X this period" — the company-wide notification-health dashboard tile. `company_id` leads as the mandatory tenant-scoping equality filter; `status` second as the near-universal secondary equality filter (a dashboard tile asks for one specific status bucket at a time); `created_at DESC` trailing for recency ordering within that bucket.
  - *Queries served:* `SELECT * FROM notifications WHERE company_id = $1 AND status = $2 AND deleted_at IS NULL ORDER BY created_at DESC LIMIT 50`; per-status count tiles (`GROUP BY status` within one company).
- `idx_notifications_company_type_created` composite on `(company_id, notification_type, created_at DESC)` WHERE `deleted_at IS NULL` — supports the stated **Filtering** requirement's type dimension (e.g., a company admin reviewing "every Late Payment notification sent this month" as an operational/compliance check), mirroring `idx_maintenance_requests_company_category`'s rationale (Module 8 §8.1) and `idx_building_documents_company_category`'s rationale (Module 10 §10.2).
- `idx_notifications_subject_trgm` — GIN trigram index on `subject` — supports the stated **Notification Search**/**Search** requirement for staff locating a specific notification by partial/misremembered subject text, the same trigram-search rationale class as `idx_maintenance_requests_title_trgm` (Module 8 §8.1) and `idx_building_documents_document_name_trgm` (Module 10 §10.2).

**Deliberately omitted indexes:**
- No standalone `template_id` index. "Which notifications were generated from template X" is a low-frequency administrative/analytics query (e.g., evaluating whether a specific template's wording correlates with lower read rates), not a hot worklist path, the identical judgment already applied to `created_by` on `maintenance_requests` (Module 8 §8.1) and `uploaded_by` on `building_documents` (Module 10 §10.2) — adequately served, if ever needed, by a sequential scan bounded to `company_id` via the composites above.
- No standalone `priority` index. Priority-only filtering across the full historical table is not a stated query shape; where priority filtering matters operationally (a `critical`-priority worklist), it is realistically always combined with a recipient or company scope already covered by the composites above, and a dedicated priority-leading index would serve no query not already served — consistent with the "avoid unnecessary indexes" discipline applied without exception since Module 3.
- No index on `body` beyond the `subject` trigram. `subject` is this table's short, purpose-built summary field exactly analogous to `maintenance_requests.title`/`building_documents.document_name`; a second GIN index on the long-form `body` column would be write-amplification for a marginal search-quality gain on a table already targeting 50,000,000+ rows — the highest-row-count table in the entire schema after `meter_readings`, making unnecessary-index avoidance here more consequential than anywhere else in the design.

**Business Rules:**
- **Immutability after send** (§11.0): once `status` transitions to `sent`, the application must reject any further UPDATE to `subject`, `body`, `notification_type`, `recipient_user_id`, or `template_id` — enforced at the application layer today (checking the row's current `status` before permitting those specific column updates), with a `BEFORE UPDATE` trigger performing the identical check as the recommended Phase 8 hardening, mirroring the identical "application-layer today, DB-trigger hardening recommended for Phase 8" posture already used for `lease_contracts` financial-term immutability (Module 5 §5.1) and the marketplace vacancy-publish gate (Module 9 §9.0). `status` itself and `read_at` remain the two legitimately-mutable-after-`sent` columns, per the stated business rules.
- **Status transition model:** `pending → sent` (the delivery-orchestration layer successfully dispatches at least the notification's primary/required channel — the exact cross-channel success criterion is an application-layer policy decision, not modeled structurally here, since `notification_deliveries` already independently tracks each channel's own outcome); `pending → failed` (every attempted channel failed); `pending → cancelled` (an application/staff action voids the notification before it was ever sent, e.g., the underlying event it was generated for became moot — a maintenance request was resolved before its "updated" notification went out). The full state-transition **graph** (disallowing, say, a `cancelled` notification from later transitioning to `sent`) is an application-layer workflow guard, not a DB constraint, identical reasoning and identical recommended Phase 8 hardening posture already established for `maintenance_requests.status` (Module 8 §8.1) and `marketplace_listings.status` (Module 9 §9.1). What *is* enforced today at the DB level is the narrower, stateless, single-row-checkable invariant (`chk_notifications_read_requires_sent`), the same class of rule a CHECK constraint *can* express.
- Per the stated business rules, **"Failed notifications remain for audit purposes"** and **"Cancelled notifications remain for history"** — neither a `failed` nor a `cancelled` status ever triggers any automatic soft-delete, archival transition, or removal; both remain permanently queryable in the notification history and dashboard-statistics indexes exactly as `sent`/`pending` rows do, the identical "status is a fact to query against, not a trigger for deletion" philosophy already established for `marketplace_listings.status = 'archived'` (Module 9 §9.0) and expired `building_documents` (Module 10 §10.2).
- `recipient_user_id`, once set, is immutable — a notification generated for the wrong user is corrected by cancelling the mistaken row (if not yet sent) or leaving it as a permanent historical fact and generating a fresh, correctly-addressed notification (if already sent), never by repointing the FK, consistent with the "denormalized-at-write, immutable thereafter" treatment already given to genuinely structural FKs elsewhere in this schema (e.g. `marketplace_listings.apartment_id`, Module 9 §9.1).

**Soft Delete Strategy:** Standard, but deliberately narrow per the stated business rules — reserved exclusively for the genuine data-entry-error case (a notification generated against the wrong recipient by an application bug, caught and corrected before it was ever sent). A notification that reached `sent`, `failed`, or `cancelled` through its ordinary lifecycle is never soft-deleted on that basis alone, per the explicit "remain for audit purposes"/"remain for history" business rules above — the identical narrow-soft-delete philosophy already applied to `building_documents` (Module 10 §10.2) and `marketplace_listings` (Module 9 §9.1), where the row's ordinary end-of-life is expressed through its own status value, not deletion.

**Audit Requirements:** Every mutation logged to `audit_logs`; `status` transitions (especially to `failed`, an operational-health signal) are treated as standard-severity events, while any soft-delete is treated as elevated-severity given it represents a correction to what was actually sent to a real recipient. Given the 50,000,000+ row scale target, the notification-generation event itself (an application-layer INSERT) is the dominant `audit_logs`-adjacent write on this table — read events (`read_at` updates) are deliberately **not** separately mirrored into `audit_logs` for every occurrence, since "user read their own notification" is a routine, non-security-relevant UX event with no accountability weight, avoiding pure write-amplification noise at a volume that would otherwise meaningfully stress `audit_logs` itself, the identical restraint already applied to routine `current_number` increments on `company_receipt_sequences` (Module 7 §7.4).

**Future Scalability Notes:** Explicitly named in the scale target (50,000,000+ rows) — the second-highest row-count table in the entire schema after `meter_readings` (100,000,000+). Evaluated against, and included in, partitioning — full reasoning in §11.4.

## 11.3 Table: `notification_deliveries`

**Purpose:** Supports delivering a single logical notification across one or more channels (email, SMS, WhatsApp, in-app), each with its own independent attempt/retry lifecycle — the channel-level fulfillment record behind every `notifications` row.

**Business Description:** A single notification is rarely delivered through exactly one channel in a mature multi-channel product — a high-priority rent-due reminder might simultaneously go out via email, SMS, and in-app, each of which succeeds, fails, or retries independently of the others. This table is the per-channel delivery-attempt record for one notification, giving the platform a direct, queryable answer to "did this specific channel actually deliver this specific notification, and if not, why."

**Columns:**

| Column Name | PostgreSQL Data Type | Nullable | Default | Description |
|---|---|---|---|---|
| id | UUID | NO | uuid_generate_v7() | Primary key |
| company_id | UUID | NO | — | Denormalized tenant scope, see §11.0 |
| notification_id | UUID | NO | — | FK to `notifications` — the stated "Notification" field; every delivery record belongs to exactly one notification |
| delivery_channel | delivery_channel_enum | NO | — | `email` \| `sms` \| `whatsapp` \| `in_app` — the stated closed channel list |
| delivery_status | delivery_status_enum | NO | 'pending' | `pending` \| `sent` \| `delivered` \| `failed` — the stated closed status list |
| attempt_count | SMALLINT | NO | 0 | The stated "Attempt Count" field — incremented by the application on every retry, per the stated business rule "Retry attempts update AttemptCount" |
| sent_at | TIMESTAMPTZ | YES | NULL | The stated "Sent At" field — when this channel's outbound dispatch was actually transmitted to the channel provider/gateway; NULL until at least one send attempt has occurred |
| delivered_at | TIMESTAMPTZ | YES | NULL | The stated "Delivered At" field — when the channel provider confirmed actual delivery (e.g., an SMS delivery receipt, an email-open-adjacent delivery confirmation, an in-app push acknowledgment); nullable since not every channel/provider integration surfaces a distinct delivery confirmation separate from "sent" |
| failure_reason | VARCHAR(255) | YES | NULL | The stated "Failure Reason" field — required once `delivery_status = 'failed'`, e.g. "invalid phone number," "provider timeout," "recipient inbox full" |
| created_at | TIMESTAMPTZ | NO | now() | — |
| updated_at | TIMESTAMPTZ | NO | now() | — |
| created_by | UUID | YES | NULL | NULL for the overwhelming majority of rows, which are system/job-generated dispatch attempts, not staff-initiated |
| updated_by | UUID | YES | NULL | — |

**Primary Key:** `id`

**Foreign Keys:**
- `company_id` → `companies(id)` ON DELETE RESTRICT.
- `notification_id` → `notifications(id)` ON DELETE RESTRICT — the direct implementation of the stated **"Orphan delivery records"** integrity requirement; a delivery record can never exist without a valid owning notification, and the notification itself is preserved permanently as delivery-proof/audit evidence.
- `created_by`, `updated_by` → `users(id)` ON DELETE SET NULL.

**Unique Constraints:** `uq_notification_deliveries_notification_channel` on `(notification_id, delivery_channel)` — the direct implementation of the stated **"Prevent duplicate deliveries for the same notification and channel"** integrity requirement: a given notification may have at most one delivery row per channel, ever. This is **not** partial (no `WHERE deleted_at IS NULL` clause) since this table carries no `deleted_at` column at all (§11.0) — the constraint is therefore a true, permanent, whole-table uniqueness guarantee. Retries against the same channel update `attempt_count`/`delivery_status`/`sent_at`/`delivered_at`/`failure_reason` **on this same row**, in place, rather than inserting a second competing row for that channel — this is the direct structural reason `attempt_count` exists as a column at all rather than being computed as `COUNT(*)` across multiple per-attempt rows: the stated business rule "one notification may have multiple delivery records" refers to multiple *channels*, not multiple *rows per channel*, and this constraint is what makes that distinction unambiguous and database-enforced rather than a convention application code could accidentally violate.

**Check Constraints:**
- `chk_notification_deliveries_attempt_count_nonneg` — `attempt_count >= 0`.
- `chk_notification_deliveries_sent_requires_attempt` — `delivery_status = 'pending' OR attempt_count > 0` — a delivery record cannot claim to be `sent`, `delivered`, or `failed` while recording zero attempts, since every one of those three outcomes is, by definition, the result of at least one dispatch attempt having actually occurred; this is part of the structural implementation of the stated **"Invalid delivery states"** integrity requirement.
- `chk_notification_deliveries_sent_at_requires_status` — `(delivery_status = 'pending' AND sent_at IS NULL) OR (delivery_status IN ('sent', 'delivered', 'failed') AND sent_at IS NOT NULL)` — a channel dispatch cannot be recorded as sent-or-beyond without a timestamp of when that dispatch occurred, and a still-`pending` row cannot carry a `sent_at` it hasn't earned yet; the second half of the **"Invalid delivery states"** structural implementation.
- `chk_notification_deliveries_delivered_requires_delivered_at` — `delivery_status != 'delivered' OR delivered_at IS NOT NULL` — a delivery cannot be marked `delivered` without the confirmation timestamp that makes that claim meaningful.
- `chk_notification_deliveries_delivered_after_sent` — `delivered_at IS NULL OR sent_at IS NULL OR delivered_at >= sent_at` — a channel cannot confirm delivery before it was ever dispatched; the ordering half of the **"Invalid delivery states"** requirement.
- `chk_notification_deliveries_failed_requires_reason` — `delivery_status != 'failed' OR failure_reason IS NOT NULL` — a failure must carry an on-record reason, the identical dispute-prevention/diagnostic-completeness reasoning already applied to `chk_cheque_details_status_date_consistency`'s `bounced` branch (Module 6 §6.2) and `chk_contract_terminations_deduction_reason` (Module 5 §5.3) — an unexplained failure gives operations staff nothing to act on when investigating a delivery-health incident.

**Indexes:**
- `uq_notification_deliveries_notification_channel` (above) — doubles as **the** "get all delivery attempts for this notification" lookup (`WHERE notification_id = $1`), the notification-detail drill-down every support/troubleshooting screen needs ("did this actually go out, and on which channels"). Preferred over a plain composite index for the identical reason given for `uq_listing_images_listing_display_order` (Module 9 §9.2) and `uq_marketplace_listings_one_active_per_apartment` (Module 9 §9.1): it is simultaneously the integrity constraint *and* the performance index, with zero risk of the two drifting out of sync.
- `idx_notification_deliveries_company_status_sent_at` composite on `(company_id, delivery_status, sent_at DESC)` WHERE `delivery_status = 'failed'` — a deliberately narrow, partial-on-status index purpose-built for the single highest-operational-value screen named in the brief: **Failed Deliveries** — the delivery-health dashboard's "what's currently broken" worklist (e.g., an SMS provider outage causing a spike in failures that operations needs to see and triage immediately). This mirrors the exact `idx_rent_payments_late_overdue` (Module 6 §6.1) / `idx_notifications_recipient_unread` (§11.2 above) narrow-partial-index pattern reserved for the one query that matters most operationally.
  - *Queries served:* `SELECT * FROM notification_deliveries WHERE company_id = $1 AND delivery_status = 'failed' ORDER BY sent_at DESC LIMIT 50` (the failed-deliveries ops dashboard); a platform-wide (cross-company, admin-console) variant of the same query for provider-outage monitoring.
  - *Expected improvement:* because this index only ever contains currently-failed rows (a small, bounded fraction of the 150,000,000+ target at any given time — the large majority of deliveries eventually succeed and never enter this partial index at all), it stays small and fast indefinitely regardless of how large the table's full historical row count grows, the identical durability argument already made for every other narrow operational-worklist partial index in this schema.
- `idx_notification_deliveries_company_channel_created` composite on `(company_id, delivery_channel, created_at DESC)` — supports the stated **Delivery History** requirement at the company-wide operational level (e.g., "show every SMS delivery attempt this week," a channel-specific reconciliation/cost-tracking screen, since SMS/WhatsApp delivery typically carries a per-message provider cost worth auditing), mirroring `idx_expense_receipts_company_issued_at`'s rationale (Module 7 §7.2) and `idx_building_documents_company_category`'s rationale (Module 10 §10.2) for the equivalent "company-wide, dimension-filtered" access shape.
- `idx_notification_deliveries_notification_id` — **not created as a separate index**; fully subsumed by the leftmost prefix of `uq_notification_deliveries_notification_channel(notification_id, delivery_channel)` above. Called out explicitly here (rather than silently shipping a redundant second index) for the identical "avoid unnecessary indexes, catch the redundancy" discipline already demonstrated for `idx_role_permissions_role_id` (Module 3 §3.5) and `idx_listing_images_listing_display_order` (Module 9 §9.2).

**Deliberately omitted index:** no standalone `delivery_channel` index without `company_id`/`notification_id` leading. "Every WhatsApp delivery platform-wide" independent of company or notification scope has no realistic product query (channel-level cost/health analysis is always at minimum company-scoped, already served by `idx_notification_deliveries_company_channel_created` above) — a bare `delivery_channel`-leading index would additionally be poor cardinality (only four possible values) and would serve no query not already served by the composite, consistent with the "avoid unnecessary indexes" discipline applied without exception since Module 3.

**Business Rules:**
- A delivery row is created once per `(notification_id, delivery_channel)` pair, at the moment the delivery-orchestration layer first attempts that channel — never re-created on retry. Every retry is an application-orchestrated `UPDATE` to the same row: `attempt_count` increments, `delivery_status`/`sent_at`/`delivered_at`/`failure_reason` are refreshed to reflect the latest attempt's outcome, per the stated **"Retry attempts update AttemptCount"** business rule. This is a deliberate, explicitly-justified departure from this schema's otherwise-consistent "corrections are additive new rows, never in-place mutation" philosophy (applied to `meter_readings`, `contract_status_history`, `maintenance_status_history`) — the difference here is that a delivery *attempt history* beyond "how many times, and what was the most recent outcome" carries no stated business requirement (unlike a lease's status timeline or a meter's full reading history, both of which are directly product-facing historical views), so collapsing retries into one row's `attempt_count` counter is proportionate to the actual stated need rather than under- or over-engineering it; if a future requirement genuinely needs a full per-attempt timeline (each retry's own timestamp and failure detail individually), that would be a clean additive extension (a child `notification_delivery_attempts` table), not a redesign of this row's current shape.
- `delivery_status` transitions follow `pending → sent → delivered` (the happy path) or `pending → sent → failed` / `pending → failed` (a dispatch-time rejection with no send ever occurring) — the full transition graph is an application-layer concern, not a DB constraint, identical reasoning to every other status-machine table in this schema; what the CHECK constraints above enforce is the narrower, stateless, single-row-checkable date/reason-correlation rules.
- `company_id` and `notification_id` are set once at INSERT and never reassigned — a delivery record's identity as "this channel's attempt at delivering this specific notification" is fixed at creation, consistent with the "denormalized-at-write, immutable thereafter" treatment already given to structural FKs throughout this schema.

**Soft Delete Strategy:** **Not applicable — no `deleted_at`/`deleted_by` columns exist on this table at all.** Per the stated business rule "Delivery history must never be deleted," and per the full rationale in §11.0, this is a deliberate, explicitly-documented deviation from the Global Convention, distinct in kind from the pure-append-only deviation class (`meter_readings`, `login_history`): this table's rows *are* mutated in place (retries), but are never removed, soft or hard, by design.

**Audit Requirements:** Standard `audit_logs` coverage for `delivery_status` transitions, particularly transitions into `failed` (an operational-health signal worth the same traceability as a bounced-cheque transition, Module 6 §6.2, though calibrated to `warning` rather than `critical` severity — a single failed SMS delivery is a real but comparatively low-stakes event with a straightforward retry/fallback-channel path, the identical severity-calibration reasoning already applied to failed `efawateercom_transactions` attempts, Module 7 §7.5). Routine `attempt_count` increments that do not also change `delivery_status` are **not** separately audit-logged, the identical write-amplification-avoidance reasoning already applied to routine counter increments on `company_receipt_sequences` (Module 7 §7.4).

**Future Scalability Notes:** Explicitly named in the scale target (150,000,000+ rows) — the single highest-row-count table in the entire schema, exceeding even `meter_readings` (100,000,000+). Evaluated against, and included in, partitioning — full reasoning in §11.4.

## 11.4 Scalability at Target Scale

| Scale point | Impact |
|---|---|
| 10,000 companies | Trivial for `notification_templates` — even generously assuming every company defines the ten seeded defaults plus several custom variants per type, this table stays in the low hundreds of thousands of rows platform-wide, comfortably single-table forever, the identical conclusion already reached for `document_categories` (Module 10 §10.4). |
| 50,000,000 notifications | **This module's first central scalability decision.** Unlike `marketplace_listings` (Module 9 §9.5) or `maintenance_requests` (Module 8 §8.6) — both deliberately excluded from partitioning because their dominant queries are status/feature-flag-bounded rather than date-range-bounded — `notifications` genuinely meets the same partitioning test `meter_readings` (Module 4 §4.8), `audit_logs`/`login_history` (Module 3 §3.11), and `rent_payments` (Module 6 §6.4) meet: it is overwhelmingly append-heavy (a notification, once generated, is only ever touched again for a `status`/`read_at` update in the near term after creation, then becomes read-mostly permanent history), naturally time-ordered via `created_at`, and every stated query shape (User Notification History, Unread Notifications, Dashboard Statistics) is either bounded to one recipient's own bounded row count (the `idx_notifications_recipient_*` composites, which remain efficient regardless of partitioning) or a recent/bounded date range at the company level (dashboard statistics ask about "this week"/"this month," not "all notifications ever"). **Recommendation: RANGE partition `notifications` by `created_at`, monthly** — closer to the `meter_readings`/`audit_logs`/`login_history` monthly convention than to `rent_payments`' quarterly deviation (Module 6 §6.4), specifically because this table's write density is genuinely comparable to those three high-frequency event-log tables (every property-management event platform-wide — a lease signed, a payment received, a maintenance ticket updated, a document nearing expiry — can generate a notification row), not to `rent_payments`' comparatively low, billing-cycle-bound density. At 50,000,000+ rows, a monthly partition holds on the order of low-single-digit millions of rows at full target scale, keeping per-partition indexes small and VACUUM cycles fast. |
| 150,000,000 notification_deliveries | **This module's second, and the schema's single largest, scalability decision.** `notification_deliveries` scales as a multiple of `notifications` (roughly 1–4 delivery rows per notification, depending on how many channels a given notification fans out to) and inherits the identical time-ordered, append-heavy-then-read-mostly shape as its parent, with every stated query (Delivery History, Failed Deliveries) already served by partial/composite indexes scoped to a company/channel/status subset rather than a full-table scan. **Recommendation: RANGE partition `notification_deliveries` by `created_at`, monthly**, the same grain and the same justification as `notifications` — the two tables' partition boundaries should align on the same monthly calendar periods so that a query spanning both (e.g., "notifications and their delivery outcomes for March 2026") benefits from matching partition pruning on both sides without a cross-partition-boundary mismatch. At 150,000,000+ rows and continuing to grow at the fastest rate of any table in the schema, monthly partitioning is not optional headroom here the way it might be for a smaller table — it is load-bearing for keeping `uq_notification_deliveries_notification_channel`'s own index (which must be maintained on every INSERT and every retry UPDATE) from degrading as history accumulates. |

**Why this module deviates from Module 9's/Module 8's "large row count does not automatically mean partition" precedent.** `marketplace_listings` and `maintenance_requests` were both correctly excluded from partitioning despite large row-count targets specifically because their *dominant* queries are not date-range-bounded — an old-but-still-`published`/`open` row is exactly as relevant to those tables' hottest query as a brand-new one. `notifications`/`notification_deliveries` are the opposite case: once a notification has been sent, read (or not), and its deliveries resolved, it recedes into pure historical record with no ongoing "is this still active" query shape comparable to an open maintenance ticket or a published listing — the closest analogue in this schema is precisely `meter_readings`/`audit_logs`/`login_history`, all genuinely time-ordered event logs, not `marketplace_listings`/`maintenance_requests`'s status-bounded-worklist shape. This module's partitioning recommendation is therefore the correct, non-mechanical application of the same query-pattern-driven test used throughout this schema — it happens to land on "partition," where the two most recent prior modules happened to land on "don't," precisely because the underlying query shapes are genuinely different, not because of any inconsistency in the test being applied.

**Partition key column requirement:** `created_at` already exists as a `NOT NULL` column with no default dependency on both tables — no schema addition is needed to introduce partitioning later, only the table-rebuild migration itself (`CREATE TABLE ... PARTITION BY RANGE`, backfill, swap), flagged here so it is planned for rather than discovered as a surprise once these tables are already at their multi-hundred-million-row target, consistent with the standing convention established since Module 3 §3.11.

**Should `notification_templates` be revisited if `notifications`/`notification_deliveries` are partitioned?** No structural change is required — a partitioned parent's (or, here, a partitioned *sibling's*) child/reference tables with a simple FK to another table's `id` continue to work identically in PostgreSQL regardless of whether that other table is partitioned, identical to the conclusion already reached for `cheque_details`/`payment_allocations` against a partitioned `rent_payments` (Module 6 §6.4) and for the Module 7 receipt tables against a partitioned `expenses`.

## 11.5 Database Integrity Summary

| Risk | Prevention Mechanism | Explanation |
|---|---|---|
| Duplicate deliveries for the same notification and channel | `uq_notification_deliveries_notification_channel` on `(notification_id, delivery_channel)`, whole-table (not partial, since this table has no `deleted_at`) | At most one delivery row per notification per channel, ever — retries update the existing row's `attempt_count`/status fields rather than inserting a competitor |
| Invalid notification states | `chk_notifications_read_requires_sent` | A notification cannot be recorded as read unless it was actually sent — a `failed`/`cancelled`/`pending` row cannot carry a `read_at` |
| Invalid delivery states | `chk_notification_deliveries_sent_requires_attempt`, `chk_notification_deliveries_sent_at_requires_status`, `chk_notification_deliveries_delivered_requires_delivered_at`, `chk_notification_deliveries_delivered_after_sent` | A comprehensive set of CHECK constraints enforcing both status/date-field correlation and date ordering — no lifecycle-inconsistent delivery row is representable |
| Invalid read timestamps | `chk_notifications_read_at_not_future`, `chk_notifications_read_at_after_created` | A notification cannot be read before it was generated or at a point in time that hasn't happened yet |
| Orphan delivery records | `notification_deliveries.notification_id` `NOT NULL` with a real FK, `ON DELETE RESTRICT` | No delivery record can exist without a valid owning notification; a notification can never be hard-deleted while any delivery record references it |
| Blank subjects | `chk_notification_templates_subject_not_blank`, `chk_notifications_subject_not_blank` | Enforced independently at both the template level and the rendered-notification level — a whitespace-only subject carries no informational value at either layer |
| Blank message bodies | `chk_notification_templates_body_not_blank`, `chk_notifications_body_not_blank` | Same reasoning, applied to the body field at both layers |
| Duplicate template names within a company | `uq_notification_templates_company_name` on `(company_id, template_name)` | Company-scoped, not global — two different companies may both legitimately have a "Rent Due — Standard" template |
| Failed delivery with no recorded reason | `chk_notification_deliveries_failed_requires_reason` | A failure must carry an on-record reason, giving operations staff a diagnostic starting point |

## 11.6 Performance Optimization Explanation

- **User Notification History:** `idx_notifications_recipient_created` — equality-leading composite with `DESC` trailing sort column, turning the single most common per-user query into a direct ordered index scan, the standard pattern applied without exception since Module 3.
- **Unread Notifications:** `idx_notifications_recipient_unread` — the narrowest, most surgical partial index in this module, scoped to exactly the currently-unread subset and reserved for the single highest-frequency read in the entire platform (the notification-bell badge count, fetched on effectively every session).
- **Notification Search / Search:** `idx_notifications_subject_trgm` — fuzzy substring search on the short subject field, the same trigram pattern already applied to `maintenance_requests.title` (Module 8), `marketplace_listings.listing_title` (Module 9), and `building_documents.document_name` (Module 10).
- **Dashboard Statistics:** `idx_notifications_company_status_created` (notification-side health tiles) and `idx_notification_deliveries_company_status_sent_at`/`idx_notification_deliveries_company_channel_created` (delivery-side health/cost tiles) together cover every stated dashboard-tile shape without a bespoke index per tile.
- **Delivery History:** `idx_notification_deliveries_company_channel_created` — the company-wide, channel-filtered delivery ledger, the natural extension of the per-notification lookup already provided by the unique constraint's own backing index.
- **Failed Deliveries:** `idx_notification_deliveries_company_status_sent_at` — a deliberately narrow partial index scoped to exactly the currently-failed subset, reserved for the single highest-operational-value delivery-health query.
- **Filtering:** every filtering dimension named in the brief (notification status, notification type, delivery channel, delivery status) is covered by one of the composite indexes above — no filtering requirement in this module lacks a matching leading-column-correct index.
- **Pagination:** every composite index with a trailing `DESC` timestamp column directly supports keyset pagination (`WHERE (recipient_user_id, created_at) < ($1, $2) ORDER BY created_at DESC LIMIT 50`), the same preferred-over-`OFFSET` strategy established since Module 3 §3.10 — essential here given this module contains the schema's two largest tables by projected row count.
- **Write-Path Consideration:** `notification_deliveries`' unique constraint on `(notification_id, delivery_channel)` is evaluated on every INSERT and every retry UPDATE — at 150,000,000+ rows and growing, this is the module's one write-path-critical index, comparable in kind (though not in aggregate volume) to `payment_allocations`' write-path-critical indexes (Module 6 §6.6); no other index in this module sits inside a write-path aggregate query, so this is the single index prioritized above the module's read-side convenience indexes during physical design.

## 11.7 Security & Multi-Tenant Isolation

- **RBAC:** Notification generation, template management, and delivery-retry actions are gated by existing `notifications.send`/`notifications.manage_templates`-style permission keys (Module 3, `permissions`) resolved via `role_permissions` — no new RBAC machinery introduced structurally in this module; it consumes the existing platform-wide permission catalog exactly as every prior module has.
- **Users may only access their own notifications — the one genuinely per-row (not merely per-tenant) access restriction in this module.** Every prior module's tenant-isolation story stops at `company_id` — any authorized staff member within a company can see any of that company's `building_documents`/`maintenance_requests`/`expenses` rows, subject only to RBAC permission gating, not to a further per-row ownership check. `notifications` is different: the stated requirement "Users may only access their own notifications" means the read path must filter on **both** `company_id` (tenant isolation) **and** `recipient_user_id = current_setting('app.current_user_id')::uuid` (row-level ownership) — a company admin does not get to browse another staff member's personal notification inbox merely by virtue of shared tenant membership and a broad RBAC grant, the same "differentiated intra-tenant access" class of requirement `building_documents.is_confidential` introduced in Module 10 §10.6, though simpler here since it's a fixed ownership check rather than a permission-gated exception. The RLS policy shape is therefore `USING (company_id = current_setting('app.current_company_id')::uuid AND recipient_user_id = current_setting('app.current_user_id')::uuid)` for ordinary end-user access, with a separate, explicitly permission-gated `admin`/`notifications.view_all`-style bypass path (mirroring `documents.view_confidential`'s shape, Module 10 §10.6) reserved for legitimate company-admin support/troubleshooting access to another user's notification history — flagged here as the same kind of permission-gated RLS predicate Module 10 §10.6 already recommended deferring to Phase 8 hardening, for the identical reason (it is the first RLS policy in this module depending on resolved session-identity state beyond tenant identity alone, warranting its own dedicated design pass rather than being finalized as a byproduct of this module).
- **Audit Logs:** Every table in this module writes to `audit_logs` on mutation per the Global Convention; `notification_templates` wording edits, `notifications.status` transitions, and `notification_deliveries.delivery_status` transitions to `failed` are logged as detailed per-table above.
- **Multi-Tenant Isolation:** All three tables in this module carry a directly-populated `company_id` and are RLS-ready under the standard `USING (company_id = current_setting('app.current_company_id')::uuid)` policy, layered — for `notifications` specifically — with the recipient-ownership predicate described above. No table in this module needs the Marketplace's public-read carve-out (Module 9 §9.7) — every row in every table here belongs unambiguously to one company with a specific, identifiable, authenticated recipient, with no legitimate cross-tenant or anonymous-public access case.
- **Soft Delete:** Standard on `notification_templates`; narrow-scope standard on `notifications` (§11.2); **explicitly not applicable** to `notification_deliveries` (§11.0/§11.3), which carries no `deleted_at`/`deleted_by` columns at all per the stated "must never be deleted" business rule.
- **Content Confidentiality:** A notification's rendered `subject`/`body` may itself contain sensitive personal or financial data (a rent amount, a maintenance detail, a document-expiry warning naming a specific legal filing) — the recipient-ownership RLS predicate above is therefore not merely an access-control nicety but the direct mechanism protecting PDPL-covered personal data (Phase 1 §1.29's PDPL framing) from being visible to any authenticated party other than its intended recipient or an explicitly-permissioned admin.

## Module 11 (Notifications) — Architecture Review

- **PostgreSQL Best Practices:** UUIDv7 PKs throughout; `TIMESTAMPTZ` for every point-in-time column in this module (`read_at`, `sent_at`, `delivered_at`, audit columns) — this module introduces no genuine calendar-`DATE` concept at all (unlike every prior module's `issue_date`/`expiry_date`-style fields), since every temporal fact here is a precise moment, not a calendar day, correctly reflected by using `TIMESTAMPTZ` exclusively rather than reflexively including a `DATE` column pattern that wouldn't fit. No monetary columns exist in this module, so the `NUMERIC(12,3)`/`currency` convention is not applicable here — correctly absent, the same "correctly absent" call already made for Module 8's maintenance tables and Module 10's documents tables.
- **Referential Integrity:** Every FK in this module is `NOT NULL` and `RESTRICT`-on-delete for the structural parent-child relationships (`recipient_user_id`, `template_id`, `notification_id`), except the standard `SET NULL` actor-attribution columns (`created_by`/`updated_by`/`deleted_by`) — consistent with the platform-wide "preserve history, sever only the actor-attribution edge" pattern established in every prior module. This module introduces no nullable structural FK anywhere except `notifications.template_id`, which is nullable by explicit stated requirement ("Template (optional)") rather than by any structural necessity — every other FK in this module is mandatory, the same narrow-scope consequence already noted for Module 9's tables.
- **Constraint Quality:** The `notifications`/`notification_deliveries` status-machine CHECK constraints were deliberately reviewed against the real-world "a channel can fail without ever having been marked sent" case (`chk_notification_deliveries_sent_at_requires_status` correctly allows `pending → failed` without requiring `sent_at`) and the "retry updates one row, not many" design was deliberately chosen over a full per-attempt history table given the stated requirements — both called out explicitly here as constraint/schema shapes that were considered and deliberately scoped, not applied mechanically the same way everywhere, continuing the "show the caught near-miss / deliberate scoping decision" transparency discipline established in Module 3 §3.5 and continued in every subsequent module.
- **Index Quality:** Every composite index in this module was checked for column-order correctness (equality-before-range/sort, `DESC` embedded where a query needs most-recent-first) — no index found with the wrong leading column. One genuine redundancy was identified and explicitly called out rather than silently shipped: a standalone `notification_id` index on `notification_deliveries` would be fully redundant with the leftmost prefix of `uq_notification_deliveries_notification_channel`'s own backing index (§11.3), the identical class of caught redundancy already documented for `idx_role_permissions_role_id` (Module 3 §3.5) and `idx_listing_images_listing_display_order` (Module 9 §9.2). Three further indexes were deliberately **not** created and the omission explicitly justified: a standalone `template_id`/`priority` index on `notifications` and a standalone `delivery_channel`-only index on `notification_deliveries` — all real candidates a less careful pass might add reflexively, all correctly identified as adding write cost without a corresponding read benefit given this module's actual stated query patterns, a discipline made more consequential than usual here given this module contains the schema's two largest tables.
- **Query Performance:** Every stated required query shape (User Notification History, Unread Notifications, Notification Search, Dashboard Statistics, Delivery History, Failed Deliveries, Search, Filtering, Pagination) is explicitly mapped to a specific index in §11.6, with no requirement left unaddressed and no index added without a corresponding named requirement — the same discipline as every prior module's requirement-to-index mapping.
- **Security:** Reviewed against every requirement in the module brief (§11.7) — RBAC, audit logging, multi-tenant isolation, and soft delete all confirmed present and correctly scoped. This module's one genuinely novel security consideration — a per-row (recipient-ownership), not merely per-tenant, read restriction — is addressed with an explicit, layered RLS-predicate approach rather than either ignoring the requirement's real complexity or over-claiming that standard tenant-scoped RLS alone satisfies "users may only access their own notifications," continuing the honest-layered-defense posture already established for confidential-document access (Module 10 §10.6).
- **Multi-Tenant Isolation:** Confirmed — all three tables denormalize/carry `company_id` directly (§11.0, §11.7); no table in this module needs a public-read or public-write carve-out, since every row here has a specific, identifiable, authenticated recipient with no legitimate cross-tenant or anonymous access case.
- **Future Scalability:** `notifications` and `notification_deliveries` — the two largest tables in the entire schema by projected row count — were both correctly evaluated *for* (not against) partitioning, on the same query-pattern-driven grounds already applied consistently since Module 3, and correctly distinguished from the two most recent prior modules' (`marketplace_listings`, `maintenance_requests`) opposite conclusion by identifying the genuine difference in dominant query shape (time-ordered historical record vs. status-bounded active worklist) rather than mechanically reapplying either the "large table, partition" or "large table, don't partition" precedent without re-examining the actual query patterns. `notification_templates` was correctly identified as trivially small at any realistic scale, requiring no scalability treatment at all.
- **Maintainability:** Every non-obvious modeling decision in this module — the narrowed single-recipient scope relative to Phase 1 §1.27's conceptual dual-recipient design (with the future-extension path explicitly flagged), the company-scoped-table-not-enum choice for templates mirrored from `document_categories`, the content-immutability-not-row-immutability distinction for `notifications`, the retry-updates-one-row-not-many design for `notification_deliveries`, the deliberate no-soft-delete deviation and its distinction from the pure-append-only deviation class, and the recipient-ownership RLS layering — is documented in place with its specific business and technical reasoning, continuing the "no undocumented deviation" discipline maintained without exception since Module 1.

## Overall Architecture Principles

- **Shared database, shared schema, row-level tenant isolation** via a mandatory `company_id` column plus PostgreSQL RLS, chosen over database-per-tenant or schema-per-tenant specifically for operational feasibility at a 10,000+-company target (Phase 1 §1.0).
- **Denormalization is deliberate and narrow, never reflexive.** Every table carries `company_id` directly (not just transitively through a parent chain), and several high-traffic tables additionally denormalize `building_id`/`tenant_id`/`apartment_id` — each instance justified per-table against a stated, real query requirement, never applied mechanically "because a prior module did it."
- **Cached/derived columns are always explicitly flagged as such**, with a named, single-purpose maintenance trigger and a stated performance justification — `apartments.occupancy_status`, `buildings.total_apartments_count`, `utility_meters.last_reading_value`, `rent_payments.amount_paid`/`due_date_status` — never a silent 3NF violation.
- **Every M:M relationship with business-meaningful attributes is modeled as a first-class entity**, never a bare join table — `user_company_roles`, `role_permissions`, `parking_assignments`, `payment_allocations` — per the explicit principle established in Phase 2 §2.1.
- **History is preserved by new rows, not by mutating old ones**, wherever a business fact is genuinely historical: lease renewals (`prior_contract_id` chain), subscription renewals, cheque replacement chains, and every status-history child table.
- **Every deviation from convention is documented in place with its specific reasoning**, not silently applied — the single most consistently repeated discipline across all 11 modules' Architecture Review sections.

## Normalization Strategy (3NF)

The schema is 3NF by default, with exactly four deliberate, individually-justified departure classes, each evaluated on its own merits rather than applied as a blanket policy:

1. **Small, stable, platform-governed domains as ENUMs, not lookup tables** — `governorate_enum` (12 fixed Jordanian governorates), `expense_category_enum` (12 stated categories), `notification_type_enum` (10 stated types), and every status/lifecycle enum throughout the schema. Chosen specifically where the domain is small, changes at a slower-than-product-iteration cadence, and where free text would introduce real integrity risk (typos, casing drift) for no benefit.
2. **Company-scoped lookup tables with seeded defaults, not enums, where the domain is genuinely company-extensible** — `roles`, `document_categories`, `notification_templates`. Chosen specifically where a company legitimately needs to extend or customize the domain beyond a platform-fixed list.
3. **Denormalized cache columns, always trigger-maintained and explicitly flagged** — never introduced without a named trigger and a stated query-performance justification, and never treated as a silent source of truth (the authoritative fact always lives elsewhere and is stated explicitly per-table).
4. **JSONB as a narrowly-scoped extensibility escape hatch** — `subscription_plans.feature_flags`, `audit_logs.metadata`, `efawateercom_transactions.raw_response` — used only where the alternative (a rigid column-per-feature or column-per-gateway-field schema) would require a migration for every incremental addition, and never used as a dumping ground for structured business data that has a real, queryable shape.

Every other table in the schema follows textbook 3NF without exception.

## UUID Strategy

**UUIDv7 primary keys throughout**, chosen over UUIDv4 specifically because UUIDv7 is time-ordered, keeping B-tree PK indexes append-mostly and avoiding the random-insert page-split penalty UUIDv4 causes at high write volume — the correct choice for a multi-tenant system generating IDs client-side or across distributed workers without coordination (Phase 3, Global Conventions). Since PostgreSQL 17 has no native `uuidv7()` function, every module assumes a pure PL/pgSQL `uuid_generate_v7()` function defined once in an early migration and used as every table's `id` default — zero extension dependency, trivially portable to native `uuidv7()` on a future PG18+ upgrade (Module 3 §3.0).

## Multi-Tenant Strategy

Every tenant-scoped table carries a directly-populated, `NOT NULL` `company_id` column and is RLS-ready under the standard `USING (company_id = current_setting('app.current_company_id')::uuid)` policy. Three deliberate, individually-justified deviations from this standard shape exist in the entire schema:

- `users`/`permissions` (Module 3) — intentionally platform-wide, non-tenant-scoped roots, since identity and the permission-key catalog are not themselves tenant data.
- `refresh_tokens`/`login_history` (Module 3) — no direct `company_id`; RLS is instead join-based against the owning user, since a user's own session/login history is scoped to *the user* (who may belong to multiple companies), not to a single tenant.
- `marketplace_listings`/`listing_images` (Module 9) — the schema's one deliberate, narrowly-scoped public-read carve-out, layered on top of (not replacing) standard tenant-isolated read/write, for the Marketplace's explicit cross-tenant public-browsing product purpose.
- `notifications` (Module 11) — the schema's one deliberate, narrowly-scoped *intra*-tenant row-level restriction, layered on top of standard tenant isolation, since "users may only access their own notifications" requires filtering on recipient identity in addition to tenant identity.

Every other table in the schema follows the standard shape without exception.

## Security Strategy

RBAC (`roles`/`permissions`/`role_permissions`/`user_company_roles`) is the single platform-wide authorization mechanism every module consumes — no module introduces bespoke authorization machinery of its own. Password/token storage follows industry-standard practice (Argon2id password hashing, SHA-256 token hashing, envelope-encrypted MFA secrets — never a reversible or plaintext credential). Refresh-token rotation with family-based theft detection (Module 3 §3.6) protects the session layer. Two tables introduce a security posture genuinely more complex than "tenant-isolated, RBAC-gated" — `building_documents.is_confidential` (Module 10 §10.6, a permission-gated intra-tenant read restriction) and `notifications` (Module 11 §11.7, a recipient-ownership intra-tenant read restriction) — both are addressed with the same honest, explicitly-layered application-primary/RLS-hardening-recommended posture rather than either overclaiming a simple mechanism solves them or leaving the requirement unaddressed.

## Audit Strategy

`audit_logs` (Module 3 §3.8) is the platform-wide, generic, immutable accountability trail — every mutation across every tenant-scoped table is captured here, satisfying Jordan's PDPL demonstrable-accountability requirement. Several modules additionally introduce a **purpose-built, narrower history table** for a specific first-class business workflow that a generic `audit_logs` query would serve poorly (`contract_status_history`, `maintenance_status_history`) — each explicitly justified as non-redundant with `audit_logs` (a different query shape, not a different fact) rather than accidental duplication. Severity calibration (`info`/`warning`/`critical`) is applied consistently by actual consequence, not uniformly — a bounced cheque or a refresh-token-theft event is `critical`; a routine template edit or a failed SMS delivery is `info`/`warning`.

## Soft Delete Strategy

Standard `deleted_at`/`deleted_by` on every table representing durable, correctable business data, with application queries defaulting to `deleted_at IS NULL`. Every deviation is individually documented and falls into one of three distinct classes, never conflated:

1. **Pure append-only event logs** — `meter_readings`, `login_history`, `audit_logs`, `contract_status_history`, `maintenance_status_history` — no soft delete because a row, once written, is never a candidate for removal of any kind; corrections are additive new rows.
2. **No-independent-lifecycle 1:1 configuration extensions** — `company_settings`, `building_addresses`, `company_receipt_sequences` — no soft delete because the row's entire lifecycle is bound to its parent's.
3. **Explicit "must never be deleted" business mandate on a table whose rows ARE mutated in place** — `notification_deliveries` (Module 11) — the one instance of this specific class in the schema, distinguished explicitly from class 1 because the rows here are legitimately updated (retries) even though never deleted.

Every table not falling into one of these three documented classes uses the standard soft-delete pattern, and several tables additionally narrow soft-delete's *scope* (reserved strictly for genuine data-entry error, never for ordinary lifecycle end-of-life, which is instead expressed through a `status` value) — `lease_contracts`, `rent_payments`, `marketplace_listings`, `building_documents`, `notifications` — each individually justified against its own stated business rules.

## Indexing Strategy

Every index in the schema is mapped to a specific, named, stated query requirement — no module ships an index without a corresponding documented access pattern, and every module's Architecture Review explicitly calls out both genuine redundancies caught during design (and removed) and reflexive-but-rejected candidate indexes (and why they were correctly omitted). Recurring, consistently-applied patterns:

- **Composite indexes with equality columns leading, range/sort columns trailing** (often `DESC` for "most recent first"), turning filter-then-sort into a single ordered index scan — applied without exception from Module 3 onward.
- **Partial indexes scoped to the actively-relevant row subset**, keeping index size proportional to live/urgent data rather than cumulative history — `idx_apartments_company_occupancy_bedrooms`, `idx_rent_payments_late_overdue`, `idx_building_documents_expiring`, `idx_notifications_recipient_unread`, and many others.
- **Partial unique indexes as the "at most one active row per resource" enforcement mechanism**, simultaneously serving as both the integrity constraint and the performance index — `uq_lease_contracts_one_active_per_apartment`, `uq_company_subscriptions_one_active`, `uq_parking_assignments_active_spot`, `uq_marketplace_listings_one_active_per_apartment`, `uq_listing_images_one_cover`, `uq_notification_deliveries_notification_channel`.
- **GIN trigram indexes** for every stated fuzzy/substring search requirement on a short, purpose-built display-name field, deliberately never extended to long-form description fields for marginal search-quality gain against real write-amplification cost.
- **Keyset pagination support** (a trailing `DESC` timestamp column on nearly every high-volume composite) preferred over `OFFSET`-based pagination throughout, flagged explicitly as essential on the schema's largest tables.

## Scalability Strategy

Partitioning decisions are made **exclusively on query-pattern grounds, never on row count alone** — this is the single most consistently reinforced engineering discipline across all 11 modules. Tables meeting the test (append-heavy, naturally time-ordered, dominant queries genuinely bounded to a recent/bounded date range) are partitioned; tables failing it are explicitly evaluated and excluded even at very large row counts, with the reasoning made explicit each time rather than defaulting to either "large table, must partition" or "prior module didn't partition a similar table, so don't."

**Partitioned tables**, by `RANGE` on their respective date column:
- `meter_readings` — monthly (Module 4 §4.8), the schema's original partitioning precedent.
- `audit_logs`, `login_history` — monthly (Module 3 §3.11).
- `rent_payments` — quarterly, a deliberate calibration down from the monthly convention given its comparatively lower write density (Module 6 §6.4).
- `expenses` — yearly, a further deliberate calibration given an even lower and less regular write density than `rent_payments` (Module 7 §7.6).
- `notifications`, `notification_deliveries` — monthly, aligned to the same calendar boundaries on both tables (Module 11 §11.4) — the schema's two largest tables by projected row count.

**Large tables deliberately excluded from partitioning**, each with an explicit query-pattern-driven justification: `apartments` (Module 4 §4.4), `lease_contracts` (Module 5 §5.8), `maintenance_requests` (Module 8 §8.6), `marketplace_listings` (Module 9 §9.5) — all because their dominant queries are status/attribute-bounded, not date-range-bounded, so a date-based partition key would not prune the working set for the query that actually matters most. Every FK-equality-lookup-dominant child table throughout the schema (`payment_allocations`, `cheque_details`, both receipt tables, `maintenance_request_attachments`/`comments`, `listing_images`, `viewing_requests`, `building_documents`) is likewise evaluated and excluded on the same grounds — row count alone never justifies partitioning in this design.

## PostgreSQL Best Practices Followed

- UUIDv7 PKs throughout, with an explicit PG17-compatible generation strategy.
- `TIMESTAMPTZ` for every point-in-time column, `DATE` (never `TIMESTAMPTZ`) for every genuine calendar-date concept — applied correctly and consistently from Module 5 onward, with the distinction called out explicitly wherever a module introduces no `DATE` columns at all (Module 11) rather than reflexively forcing one in.
- `NUMERIC(12,3)` for every JOD-denominated monetary column, always paired with an explicit `currency CHAR(3)` column, never a hardcoded currency assumption, future-proofing GCC multi-currency expansion.
- Partial indexes and partial unique constraints used consistently wherever the live/relevant row subset is meaningfully smaller than the cumulative historical row set.
- `RESTRICT` as the default `ON DELETE` behavior for every structural parent-child FK preserving financial/legal/operational history; `SET NULL` reserved specifically for actor-attribution columns and genuinely optional structural links; `CASCADE` reserved specifically for true no-independent-lifecycle 1:1/1:many extensions.
- Every CHECK constraint expresses a genuinely stateless, single-row-checkable invariant; every cross-row/cross-table invariant (circular renewal chains, over-allocation, vacancy-gated publishing, status-transition graphs) is explicitly layered — application-primary defense today, a documented and specific trigger-based hardening recommended for Phase 8 — rather than either left unaddressed or falsely claimed to be fully DB-enforced by a CHECK constraint alone.

## Design Decisions Intentionally Rejected (and Why)

- **Database-per-tenant / schema-per-tenant multi-tenancy** — rejected as operationally infeasible past a few hundred tenants at this platform's target scale; row-level isolation via `company_id` + RLS chosen instead (Phase 1 §1.0).
- **A separate `contract_renewals` table** — rejected in favor of `lease_contracts.prior_contract_id` self-referencing chain; a renewal genuinely *is* a new lease contract with lineage, not a structurally distinct event type (Phase 1 §1.13, Phase 2 §2.4).
- **Polymorphic `source_type`/`source_id` receipts** — rejected in favor of table-per-concrete-type (`rent_payment_receipts`, `expense_receipts`), since a polymorphic FK cannot be database-enforced and Prisma has no native polymorphic-relation support; a sequentially-numbered legal financial artifact requires structural, non-negotiable FK integrity (Phase 1 §1.20).
- **A dual-nullable `user_id`/`tenant_id` recipient shape on `notifications`** — deferred (not rejected outright) in favor of a single mandatory `recipient_user_id`, matching Module 11's explicit narrowed field list; the dual-recipient case remains a clean, explicitly-flagged future additive extension rather than built prematurely against a requirement not actually stated in this pass (Module 11 §11.0).
- **Full dual-mode (`INTERNAL`/`EXTERNAL`) Marketplace listings** — narrowed to INTERNAL-only in Module 9, matching that module's explicit field list; the original Phase 1 §1.24 dual-mode CHECK-constraint design remains the correct blueprint for a future extension, not contradicted, simply not built in this pass.
- **A separate confidential-documents table** — rejected in favor of a single `is_confidential` flag plus layered application/RLS access control on `building_documents`; a confidential and non-confidential document are the same business object differing only in read-access policy, not a structural/business-object difference (Module 10 §10.6).
- **A full per-attempt delivery-history table for `notification_deliveries`** — rejected in favor of one row per `(notification, channel)` with an `attempt_count` counter, matching the actual stated requirement ("Retry attempts update AttemptCount," not "retain every individual attempt's own timeline"); flagged as a clean future additive extension should that finer-grained requirement ever be stated (Module 11 §11.3).
- **Mechanically reapplying monthly partitioning to every large table** — rejected; `rent_payments` and `expenses` were each individually recalibrated to a coarser grain (quarterly, yearly respectively) based on their own actual write-density profile rather than defaulting to the `meter_readings`/`audit_logs` monthly convention (Module 6 §6.4, Module 7 §7.6).
- **Mechanically partitioning every large table regardless of query pattern** — rejected; `apartments`, `lease_contracts`, `maintenance_requests`, and `marketplace_listings` were each evaluated and excluded despite large row-count targets, since row count alone was never treated as sufficient justification anywhere in this design.
- **A `lease_guarantors` table and a `efawateercom_billers` table** — neither is part of PropertyOS; Module 5's Leasing tables are limited to `lease_contracts`, `contract_terminations`, `contract_status_history`, and `contract_documents`, and Module 7's `efawateercom_transactions` carries no dependency on a biller-registration table.
