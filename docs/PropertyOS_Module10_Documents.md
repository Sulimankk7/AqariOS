# MODULE 10 — DOCUMENTS

Continuation of `PropertyOS_Phase3_Physical_Design.md`, `PropertyOS_Module4_Properties.md`, `PropertyOS_Module5_Leasing.md`, `PropertyOS_Module6_RentPayments_Updated.md`, `PropertyOS_Module7_FinancialOperations_Updated.md`, `PropertyOS_Module8_Maintenance.md`, and `PropertyOS_Module9_Marketplace.md`. Applies the same Global Conventions (UUIDv7 PKs, `created_at`/`updated_at`/`created_by`/`updated_by`, soft delete, `company_id` + RLS tenant isolation, `snake_case` naming) unless a deviation is explicitly justified.

Scope for this module is deliberately narrow, per the module brief: **two tables only** — `document_categories`, `building_documents`. No versioning, document approvals, document workflows, digital signatures, OCR, AI processing, or document sharing — those are explicitly out of scope and are not introduced anywhere below, even implicitly via a stray column.

Scale target for this module: **10,000+ companies, 50,000+ buildings, 10,000,000+ documents.**

## 10.0 Module-Wide Design Decisions (read before the tables)

**Document categories are a company-managed lookup table, not a platform-wide enum.** This is a deliberate departure from the closed-enum pattern used for genuinely fixed, platform-defined domains elsewhere in this schema (`expense_category_enum`, Module 7 §7.0; `governorate_enum`, Module 4 §4.0). The module brief explicitly states "categories are managed per company," and lists ten *suggested* categories (Ownership Documents, Building License, Occupancy Permit, Municipality Documents, Utility Documents, Insurance, Contracts, Maintenance, Financial, Other) rather than a closed, product-fixed list a migration would be required to extend. A property management company in Jordan may legitimately need a category an enum wouldn't anticipate (e.g., "Civil Defense Certificates" split out from the generic Municipality bucket, or a category specific to one company's internal filing convention) — the same underlying reasoning that already led this schema to model `roles` (Module 3 §3.3) and `notification_templates` (Phase 1 §1.28) as company-scoped tables with system-seeded defaults rather than enums, applied here to document categorization. `document_categories` is therefore a real table with a real, dedicated, mandatory FK from `building_documents`, giving database-level referential integrity for "every document has a valid, currently-defined category" — an integrity guarantee a free-text category column could never give.

**The ten stated categories are seeded per company at signup, not shipped as system-wide rows.** Unlike `roles`/`permissions` (Module 3 §3.3/§3.4), which distinguish system-owned rows (`company_id IS NULL`) from tenant-custom rows, `document_categories` has no system/custom split — every row, including the ten suggested defaults, is a genuine company-scoped row (`company_id NOT NULL`). This is a deliberate simplification relative to the `roles` pattern: unlike RBAC roles, where a platform-wide immutable Owner role is a real security invariant (Phase 1 §1.3) that must never be tenant-editable, document categories carry no comparable platform-level correctness requirement — a company renaming or retiring its own "Insurance" category has no security or billing implication, so there is no need for the added structural complexity of a nullable `company_id` and its accompanying partial-uniqueness split. The application seeds the ten stated categories into a new company's own rows at signup (an application-orchestrated transaction, mirroring `company_settings`' identical auto-creation-at-signup pattern, Module 1 §1.2), after which each company's category list is fully theirs to edit, rename, or extend.

**Denormalized `company_id` on `building_documents`**, consistent with the module-wide denormalization principle established in Module 4 §4.0 and carried through every subsequent module — `building_documents` carries `company_id` directly rather than requiring a join through `buildings` to establish tenant scope, since this table is both RLS-protected directly and queried at high volume in isolation from its full parent chain (a company-wide "all Insurance documents across the portfolio" compliance query should not require joining through `buildings` just to filter by tenant).

**Confidentiality is a differentiated *intra*-tenant access concern, not a multi-tenant one — a genuinely new class of security requirement for this schema.** Every prior module's security section addressed either standard single-tenant isolation (every table except `marketplace_listings`/`listing_images`, Module 9 §9.7) or a full cross-tenant public-read carve-out (`marketplace_listings`). `building_documents.is_confidential` is neither: a confidential document (e.g., an ownership deed, a sensitive legal filing) must remain hidden from some *authenticated members of the same company* — a leasing agent or maintenance-portal user — while remaining visible to authorized roles (owner, admin, legal/compliance staff) within that same tenant. This is addressed in full in §10.6, since it requires a layered application-RBAC-plus-optional-RLS posture distinct from every other table's isolation story in this schema.

**Integration with `file_storage` follows the identical pattern established for every other document-bearing table in this schema** (`contract_documents`, Module 5 §5.5; `expense_receipts`/`rent_payment_receipts`, Module 7 §7.2/§7.3; `maintenance_request_attachments`, Module 8 §8.2; `listing_images`, Module 9 §9.2): a real, mandatory, `NOT NULL`, `ON DELETE RESTRICT` foreign key to `file_storage`, never a polymorphic or duplicated blob-metadata structure — the file's actual bytes and storage-layer metadata live in `file_storage`, centralizing upload/access-control/audit logic exactly as Phase 1 §1.32 specifies.

## 10.1 Table: `document_categories`

**Purpose:** The company-scoped classification lookup for every document attached to a building — the categorization dimension the stated "Category Filtering" and "Dashboard"-style compliance-review requirements are built against.

**Business Description:** Represents one document classification bucket for a company's building-document filing system (Ownership Documents, Building License, Occupancy Permit, Municipality Documents, Utility Documents, Insurance, Contracts, Maintenance, Financial, Other, or any additional company-defined category). Every company gets its own independent set of category rows, seeded with the ten stated defaults at signup and freely extensible thereafter.

**Columns:**

| Column Name | PostgreSQL Data Type | Nullable | Default | Description |
|---|---|---|---|---|
| id | UUID | NO | uuid_generate_v7() | Primary key |
| company_id | UUID | NO | — | Owning company — every category row belongs to exactly one company (stated requirement: "Categories are managed per company") |
| name | VARCHAR(100) | NO | — | The category's display name, e.g. "Insurance", "Building License" — free text since companies may extend beyond the ten stated defaults |
| description | VARCHAR(255) | YES | NULL | Optional free-form clarification of what belongs in this category (e.g., distinguishing "Municipality Documents" from "Building License" for a company's own staff, where the boundary might otherwise be ambiguous) |
| created_at | TIMESTAMPTZ | NO | now() | — |
| updated_at | TIMESTAMPTZ | NO | now() | — |
| created_by | UUID | YES | NULL | NULL for the ten system-seeded default rows created by the signup transaction with no human actor |
| updated_by | UUID | YES | NULL | — |
| deleted_at | TIMESTAMPTZ | YES | NULL | Soft delete |
| deleted_by | UUID | YES | NULL | — |

**Primary Key:** `id`

**Foreign Keys:**
- `company_id` → `companies(id)` ON DELETE RESTRICT.
- `created_by`, `updated_by`, `deleted_by` → `users(id)` ON DELETE SET NULL.

**Unique Constraints:** `uq_document_categories_company_name` on `(company_id, name)` WHERE `deleted_at IS NULL` — the direct implementation of the stated **"Duplicate category names within the same company"** integrity requirement. Scoped to `company_id`, not global, since two different companies routinely and legitimately both have an "Insurance" category — the same company-scoped-uniqueness reasoning already applied to `uq_lease_contracts_company_contract_number` (Module 5 §5.1) and `uq_roles_company_code` (Module 3 §3.3). Partial on `deleted_at IS NULL` so a retired category's name can be reused by a new category later, the identical partial-unique pattern used consistently since Module 3.

**Check Constraints:**
- `chk_document_categories_name_not_blank` — `length(btrim(name)) > 0` — a whitespace-only category name is not a meaningful classification bucket; mirrors `chk_maintenance_requests_title_not_blank` (Module 8 §8.1) and `chk_marketplace_listings_title_not_blank` (Module 9 §9.1) — the same cheap, structural rejection of a real data-entry failure mode applied consistently throughout this schema.

**Indexes:** None beyond the unique constraint's implicit index. `uq_document_categories_company_name`'s backing composite `(company_id, name)` already serves the one realistic access pattern this table has — "list this company's categories" (the category-picker dropdown at document-upload time, and the category-management settings screen) — as a leftmost-prefix scan on `company_id`, returned in name-sorted order for free. A dedicated standalone `company_id` index would be fully redundant with this leftmost prefix, the identical "the composite already covers it" reasoning already caught and corrected for `idx_role_permissions_role_id` (Module 3 §3.5) and `idx_listing_images_listing_display_order` (Module 9 §9.2) — called out explicitly here rather than silently shipping a redundant second index.

**Business Rules:** The ten stated default categories are seeded into a new company's own rows in the same signup transaction that creates its `company_settings` row (application-orchestrated, not a DB trigger, mirroring `company_settings`' identical auto-creation-at-signup pattern, Module 1 §1.2) — so a company's category picker is never empty on day one, with no nullable "categories not yet configured" state to handle downstream. Companies may freely rename, describe, or add categories beyond the seeded ten; there is no structural distinction between a "default" and a "custom" category row (§10.0) — both are ordinary, equally-editable rows. A category referenced by at least one `building_documents` row cannot be hard-deleted (enforced by the `RESTRICT` FK below) but may be soft-deleted to retire it from the upload picker; documents already tagged with a soft-deleted category continue to display that category's name via a query that does not apply the standard `deleted_at IS NULL` filter on the *joined* category side specifically for this display purpose — a retired category's name remains a real historical fact about a document, and hiding it from an already-tagged document's detail view would be a data-loss regression, not a correct application of the soft-delete convention.

**Soft Delete Strategy:** Standard — reserved for a company genuinely retiring a category it no longer wants offered on new uploads; not used to "delete" a category still actively selected on new documents (that's simply not applicable, since the category remains in the active picker until a staff member deliberately retires it).

**Audit Requirements:** Standard `audit_logs` coverage; category creation, renaming, and soft-delete are logged, consistent with the Global Convention — a low-severity, routine configuration event, not elevated, since a category rename has no direct financial/legal consequence.

**Future Scalability Notes:** Trivially small at any scale — even generously assuming every one of 10,000+ companies defines the ten seeded defaults plus a handful of custom categories, this table stays in the low hundreds of thousands of rows platform-wide, comfortably within single-table territory indefinitely. No partitioning or additional indexing concern at any realistic scale, the identical conclusion already reached for `company_settings` (Module 1 §1.2) and `roles` (Module 3 §3.3).

## 10.2 Table: `building_documents`

**Purpose:** Supports attaching an unlimited number of categorized, optionally-confidential documents to a building — ownership deeds, building licenses, occupancy permits, municipality filings, utility documents, insurance policies, contracts, maintenance records, financial records, and any company-defined category beyond those — integrating with the central `file_storage` governance table exactly as every other document-bearing table in this schema does.

**Business Description:** Represents one uploaded document filed against a specific building: the deed, the elevator inspection certificate, the fire-safety compliance filing, an insurance policy PDF, a scanned municipal correspondence — the compliance and legal-recordkeeping backbone Phase 1 §1.23 originally flagged as a genuine, recurring operational necessity (civil defense certificate renewal lapses being the canonical example of what this table exists to prevent through the "Expiring Documents" access pattern below).

**Columns:**

| Column Name | PostgreSQL Data Type | Nullable | Default | Description |
|---|---|---|---|---|
| id | UUID | NO | uuid_generate_v7() | Primary key |
| company_id | UUID | NO | — | Denormalized tenant scope, see §10.0 |
| building_id | UUID | NO | — | The building this document belongs to — a building may contain unlimited documents (stated requirement) |
| category_id | UUID | NO | — | FK to `document_categories` — every document belongs to exactly one category (stated requirement: "Company, Building, Category, File Storage") |
| file_id | UUID | NO | — | FK to `file_storage` — the actual uploaded file metadata/blob pointer; every document references exactly one uploaded file (stated business rule) |
| document_name | VARCHAR(255) | NO | — | The stated "Document Name" field — the short, human-facing label displayed on every document-list/search screen, e.g. "Ownership Deed — Building A", "Fire Safety Certificate 2026" |
| description | TEXT | YES | NULL | The stated "Description" field — free-form elaboration beyond the short name |
| issue_date | DATE | YES | NULL | The date the document was actually issued/executed (e.g., the date a permit was granted, the date an insurance policy took effect); nullable since not every filed document has a formally recorded issuance date (e.g., an internal scanned note filed under "Other") — see Check Constraints |
| expiry_date | DATE | YES | NULL | The date the document lapses/requires renewal (e.g., an insurance policy's or a permit's expiry); nullable since many document types — an ownership deed, a signed contract — have no expiry concept at all |
| is_confidential | BOOLEAN | NO | false | Flags a document as restricted to authorized roles only (stated requirement) — see §10.6 for the full access-control mechanism this flag drives |
| uploaded_by | UUID | YES | NULL | FK to `users` — the staff member who physically performed the upload; nullable for system-migrated/bulk-imported historical documents with no attributable uploader — see Business Rules for why this is kept distinct from `created_by` |
| created_at | TIMESTAMPTZ | NO | now() | — |
| updated_at | TIMESTAMPTZ | NO | now() | — |
| created_by | UUID | YES | NULL | — |
| updated_by | UUID | YES | NULL | — |
| deleted_at | TIMESTAMPTZ | YES | NULL | Soft delete — reserved narrowly per the stated business rule, see Soft Delete Strategy |
| deleted_by | UUID | YES | NULL | — |

**Primary Key:** `id`

**Foreign Keys:**
- `company_id` → `companies(id)` ON DELETE RESTRICT.
- `building_id` → `buildings(id)` ON DELETE RESTRICT — per Phase 2's relationship catalog (§2.1.G), building documents are compliance/legal record preserved permanently; a building can never be hard-deleted while any document references it.
- `category_id` → `document_categories(id)` ON DELETE RESTRICT — a document's categorization is structured, queryable metadata (the "Category Filtering" requirement depends on it), not merely descriptive text; a category referenced by any document can never be hard-deleted out from under it.
- `file_id` → `file_storage(id)` ON DELETE RESTRICT — the file metadata record must outlive this join row, identical reasoning to `contract_documents.file_id` (Module 5 §5.5), `maintenance_request_attachments.file_id` (Module 8 §8.2), and `listing_images.file_id` (Module 9 §9.2).
- `uploaded_by`, `created_by`, `updated_by`, `deleted_by` → `users(id)` ON DELETE SET NULL.

**Unique Constraints:** `uq_building_documents_building_file` on `(building_id, file_id)` WHERE `deleted_at IS NULL` — the same physical file should not be attached twice to the same building under two different rows (a genuine duplicate-upload data-entry error), mirroring `uq_contract_documents_contract_file` (Module 5 §5.5), `uq_maintenance_request_attachments_request_file` (Module 8 §8.2), and the general shape of this pattern applied consistently to every file-attachment table in this schema. Does **not** prevent the same file being referenced by two *different* buildings' document rows — not a realistic scenario in practice (a document is scanned/uploaded once, for one building), but not structurally harmful either, so not worth constraining against.

**Check Constraints:**
- `chk_building_documents_name_not_blank` — `length(btrim(document_name)) > 0` — the direct implementation of the stated **"Blank document names"** integrity requirement; a whitespace-only name carries no informational value and almost always indicates a client-side submission bug, mirroring `chk_document_categories_name_not_blank` above and `chk_maintenance_requests_title_not_blank` (Module 8 §8.1).
- `chk_building_documents_issue_date_not_future` — `issue_date IS NULL OR issue_date <= CURRENT_DATE` — the direct implementation of the stated **"Invalid issue dates"** integrity requirement: an issue date records something that has already happened (a document was already issued/executed), not a future-scheduling field, the identical "historical fact" reasoning applied to `request_date` (Module 8 §8.1), `expense_date` (Module 7 §7.1), and `published_date` (Module 9 §9.1) throughout this schema.
- `chk_building_documents_expiry_after_issue` — `expiry_date IS NULL OR issue_date IS NULL OR expiry_date > issue_date` — the direct implementation of the stated **"Invalid expiry dates"** integrity requirement: a document cannot be recorded as expiring before (or on the same day as) it was issued. Deliberately **not** constrained against `CURRENT_DATE` in either direction — unlike `issue_date`, `expiry_date` is legitimately either in the future (an active, not-yet-lapsed permit or policy — the normal, common case) or in the past (an already-expired document deliberately retained per the stated "Expired documents remain stored for historical purposes" business rule) — constraining `expiry_date` against `CURRENT_DATE` in any direction would reject one of these two entirely legitimate real-world states.

**Indexes:**
- `idx_building_documents_building_created` composite on `(building_id, created_at DESC)` WHERE `deleted_at IS NULL` — **the** primary **Building Documents** query (stated requirement): the building detail page's documents tab, full document list for one building, most-recently-uploaded first. `building_id` leads as the mandatory equality filter for this screen; `created_at DESC` trails so the common "newest uploads first" access is a direct ordered index scan with no separate sort step, mirroring the identical composite-with-trailing-DESC pattern established throughout Modules 3–9. Sorted by upload recency (`created_at`) rather than `issue_date`/`expiry_date` specifically because the documents tab's default view is "what did we most recently file for this building," not a date-of-issuance ledger — an intentional choice distinct from the narrower expiry-focused index below.
  - *Queries served:* `SELECT * FROM building_documents WHERE building_id = $1 AND deleted_at IS NULL ORDER BY created_at DESC LIMIT 50` (building detail page, paginated).
  - *Expected improvement:* turns a filter-then-sort over a table headed toward 10,000,000 rows into a single ordered index range-scan bounded to one building's own document count (typically dozens to low hundreds over a building's operational life, not thousands).
  - *Why preferred over a standalone `building_id` index:* identical reasoning established since Module 3 — a composite with the sort column embedded serves both the equality filter and the ordering in one structure, avoiding a separate sort step a plain single-column index would still require.
- `idx_building_documents_building_category` composite on `(building_id, category_id)` WHERE `deleted_at IS NULL` — the building-scoped shape of the stated **Category Filtering** requirement: within one building's documents tab, filtering to just "Insurance" or just "Municipality Documents." This is the more frequent, day-to-day category-filtering access pattern (a staff member working one building's compliance folder), distinct from the portfolio-wide shape below.
  - *Queries served:* `SELECT * FROM building_documents WHERE building_id = $1 AND category_id = $2 AND deleted_at IS NULL` (documents tab's category-filter tabs/dropdown).
  - *Expected improvement:* a targeted index range-scan bounded to one building's documents in one category, rather than a sequential scan of the building's full (already-modest, but not free) document set filtered in application code.
- `idx_building_documents_company_category` composite on `(company_id, category_id)` WHERE `deleted_at IS NULL` — the portfolio-wide shape of the stated **Category Filtering** requirement: a company-wide compliance-review query spanning every building at once (e.g., "show every Insurance document across the whole portfolio, so we can confirm every building actually has one on file" — a real, periodic compliance-audit workflow), mirroring `idx_expenses_company_category_date`'s rationale (Module 7 §7.1) and `idx_maintenance_requests_company_category`'s rationale (Module 8 §8.1), though without a trailing date column here for the same reason `maintenance_requests`' equivalent index omits one — a category-filtered document view is typically consumed as a full worklist (further refined client-side or by the building-scoped index above), not a strictly date-ordered report.
  - *Queries served:* `SELECT * FROM building_documents WHERE company_id = $1 AND category_id = $2 AND deleted_at IS NULL` (the portfolio-wide compliance-review screen, e.g. "all Building License documents, company-wide, to check for gaps").
  - *Why this is not redundant with the building-scoped composite above:* a company owns many buildings; answering "every Insurance document across the whole portfolio" from the `building_id`-leading index alone would require either a join through `buildings` (an extra hop this module's denormalized `company_id` is specifically designed to avoid, per §10.0) or a full-table scan filtered by `category_id` — neither acceptable at a 10,000,000-row target. Both composites are necessary because they serve two genuinely different roots of aggregation (one building vs. the whole company), the identical dual-composite justification already given for `idx_apartments_building_id` alongside `idx_apartments_company_occupancy` (Module 4 §4.4).
- `idx_building_documents_expiring` composite on `(company_id, expiry_date)` WHERE `expiry_date IS NOT NULL AND deleted_at IS NULL` — the direct implementation of the stated **Expiring Documents** requirement, and the physical mechanism behind the exact compliance risk Phase 1 §1.23 originally flagged (civil defense certificate renewal lapses): a deliberately narrow, partial-on-non-NULL-expiry index purpose-built for the scheduled renewal-reminder job's daily sweep and the "documents expiring in the next 30/60/90 days" dashboard widget. This mirrors the exact `idx_lease_contracts_expiration` (Module 5 §5.1) / `idx_marketplace_listings_expiring` (Module 9 §9.1) narrow-partial-index pattern already established for every other "upcoming expiry" requirement in this schema.
  - *Queries served:* `SELECT * FROM building_documents WHERE company_id = $1 AND expiry_date BETWEEN CURRENT_DATE AND CURRENT_DATE + INTERVAL '30 days' AND deleted_at IS NULL ORDER BY expiry_date` (the renewal-reminder job; the compliance dashboard's "expiring soon" tile).
  - *Expected improvement:* because this index only ever contains rows with a populated `expiry_date` (a meaningful but bounded fraction of the table — ownership deeds and many "Other"-category documents never populate this column at all), and the job's own date-range filter further narrows the scan to a small, near-term slice of even that subset, this stays fast indefinitely regardless of how large the table's full historical row count grows, the identical durability argument already made for `idx_rent_payments_late_overdue` (Module 6 §6.1) and `idx_marketplace_listings_expiring` (Module 9 §9.1).
- `idx_building_documents_document_name_trgm` — GIN trigram index on `document_name` — supports the stated **Search** requirement for staff locating a document by partial/misremembered name, the same trigram-search rationale class as `idx_buildings_name_trgm` (Module 4), `idx_lease_contracts_contract_number_trgm` (Module 5), `idx_maintenance_requests_title_trgm` (Module 8), and `idx_marketplace_listings_title_trgm` (Module 9).

**Deliberately omitted indexes:**
- No standalone `building_id` index — already fully covered as the leading column of `idx_building_documents_building_created`'s leftmost prefix; a separate single-column index would be redundant, the identical "composite already covers it" reasoning called out explicitly since Module 3 §3.5.
- No standalone `company_id` index — already fully covered as the leading column of `idx_building_documents_company_category`'s leftmost prefix, and RLS policy evaluation on this table's per-tenant row subset does not need a dedicated index the way a genuinely hot single-column filter would, the identical judgment already applied to `floors` (Module 4 §4.3) and `lease_guarantors` (Module 5 §5.2).
- No standalone `is_confidential` index. Confidentiality filtering is always evaluated as an access-control gate layered on top of an already-scoped query (a building's documents, a category's documents), never as the sole or leading filter of a realistic query ("show me every confidential document platform-wide" is not a stated or realistic screen) — a low-cardinality boolean column earns an index only when it is itself a primary, frequently-isolated filter, which is not the case here.
- No standalone `uploaded_by` index — "which documents did staff member X upload" is a low-frequency administrative-review query, not a hot path, the identical judgment already applied to `created_by` on `maintenance_requests` (Module 8 §8.1) and `changed_by` on `contract_status_history` (Module 5 §5.4).
- No index on `description` beyond the `document_name` trigram — `document_name` is this table's short, purpose-built summary field exactly analogous to `buildings.name`/`maintenance_requests.title`; a second GIN index on the long-form `description` column would be write-amplification for a marginal search-quality gain, the identical "avoid unnecessary indexes" conclusion already reached for `maintenance_requests.description` (Module 8 §8.1) and `marketplace_listings.listing_description` (Module 9 §9.1).

**Business Rules:**
- `uploaded_by` and `created_by` are kept as two distinct columns, mirroring the narrow, explicitly-justified exception already established for `maintenance_request_attachments` (Module 8 §8.2) rather than the single-`created_by`-suffices consolidation used for most of this schema's actor-attribution columns: document upload is one of the specific places in this schema where the *acting* user and the *audit-row-creating* user can genuinely diverge — a staff member may physically hand a paper document to an admin assistant who performs the actual system upload on their behalf, or a bulk-migration tool may create the row on behalf of a staff member who is recorded as the real-world uploader in `uploaded_by`. This is a deliberate, narrow deviation from the "one actor-attribution column suffices" default, called out explicitly here exactly as it was for `maintenance_request_attachments`, so it doesn't read as an inconsistency.
- A document's `building_id`, `category_id`, and `file_id` are set once at INSERT and never independently reassigned — a document filed against the wrong building or miscategorized is corrected by soft-deleting the mistaken row and creating a new one, not by repointing the FKs, consistent with the "denormalized-at-write, immutable thereafter" treatment already given to genuinely structural FKs elsewhere in this schema (e.g. `marketplace_listings.apartment_id`, Module 9 §9.1) — a document reference is compliance/legal evidence, not a correctable data-entry field the way `expenses.building_id` or `apartments.tenant_id` reassignment is (Module 7 §7.1, Module 8 §8.1), because unlike those cases a document's *identity as a specific filed record* is itself part of what makes it evidentiary.
- Per the stated business rule, **expired documents remain stored for historical purposes** — an `expiry_date` in the past never triggers any automatic status change, archival transition, or removal; `building_documents` has no `status` column at all (unlike `marketplace_listings`/`maintenance_requests`), since a document's relevance is not a lifecycle state to track, only a fact (`expiry_date`) to query against — "is this currently valid" is a point-in-time computation (`expiry_date IS NULL OR expiry_date >= CURRENT_DATE`) performed at read time by the application/dashboard layer, not a cached or persisted column, since there is no derived-cache performance concern here comparable to `apartments.occupancy_status` (a document's own row is never queried at a volume that would justify a maintained cache column for this single boolean fact).

**Soft Delete Strategy:** Standard, but deliberately narrow per the stated business rule — **"Soft Delete is reserved only for accidental uploads or administrative corrections."** A document that has genuinely expired is never soft-deleted on that basis alone (per the "expired documents remain stored for historical purposes" rule above); soft-delete is used exclusively for the data-entry-error case (the wrong file attached, a duplicate upload, a document filed against the wrong building before the correction described in Business Rules is applied) — the identical narrow-soft-delete philosophy already applied to `lease_contracts` (Module 5 §5.1) and `marketplace_listings` (Module 9 §9.1), where the ordinary end-of-life of a real row is expressed through a different mechanism (there, a status transition; here, simply the passage of `expiry_date` with no state change at all) rather than deletion.

**Audit Requirements:** Every mutation logged to `audit_logs`; uploads, soft-deletes, and any change to `is_confidential` are treated as elevated-severity events — flipping a document's confidentiality flag is a direct, immediate change to who can see a potentially sensitive legal/financial record, comparable in weight to the `apartment_id`/`tenant_id` reassignment events already flagged elevated-severity for `maintenance_requests` (Module 8 §8.1).

**Future Scalability Notes:** Explicitly named in the scale target (10,000,000+ rows). Evaluated against, and excluded from, partitioning — full reasoning in §10.4.

## 10.3 Database Integrity Summary

| Risk | Prevention Mechanism | Explanation |
|---|---|---|
| Orphan documents | `building_documents.building_id` `NOT NULL` with a real FK, `ON DELETE RESTRICT` | No document can exist without a valid owning building; a building can never be hard-deleted while any document references it |
| Orphan files | `building_documents.file_id` `NOT NULL` with a real FK to `file_storage`, `ON DELETE RESTRICT` | The uploaded file's metadata record must outlive the join row referencing it, mirroring `contract_documents.file_id` (Module 5 §5.5) and every other file-attachment table in this schema |
| Duplicate category names within a company | `uq_document_categories_company_name` on `(company_id, name)` | Company-scoped, not global — two different companies may both legitimately have an "Insurance" category |
| Invalid issue dates | `chk_building_documents_issue_date_not_future` | An issue date records something that has already happened; a document cannot be recorded as issued on a future date |
| Invalid expiry dates | `chk_building_documents_expiry_after_issue` | An expiry date, when set alongside an issue date, must fall strictly after it — a document cannot be recorded as expiring before (or on) the day it was issued |
| Blank document names | `chk_building_documents_name_not_blank` | A whitespace-only document name carries no informational value and almost always indicates a client-side submission bug |
| Blank category names | `chk_document_categories_name_not_blank` | Same reasoning, applied to the category-name field |
| Invalid category references (dangling `category_id`) | `building_documents.category_id` `NOT NULL` with a real FK, `ON DELETE RESTRICT` | A document's categorization is structured metadata the "Category Filtering" requirement depends on; a category referenced by any document can never be hard-deleted out from under it |
| Duplicate file attached twice to the same building | `uq_building_documents_building_file` on `(building_id, file_id)` | Catches the genuine duplicate-upload data-entry error while allowing the same file to (in principle, though not realistically) appear against a different building |

## 10.4 Scalability at Target Scale

| Scale point | Impact |
|---|---|
| 10,000 companies | Trivial for `document_categories` — even generously assuming every company defines the ten seeded defaults plus several custom categories, this table stays in the low hundreds of thousands of rows platform-wide, comfortably single-table forever. |
| 50,000 buildings | Trivial impact on `building_documents`' indexing strategy — `building_id` remains a low-to-moderate-cardinality leading column even at this scale, and every composite index above stays efficient since it filters to one building's (or one company's) own bounded document subset, never a platform-wide scan. |
| 10,000,000 building_documents | **This module's central scalability question.** At 10,000,000 rows across 50,000 buildings, average document density is roughly 200 documents/building — comfortably within the range every composite index above (all leading with `building_id` or `company_id`) keeps fast regardless of the table's total historical size, since no stated query shape (Building Documents, Category Filtering, Expiring Documents, Search) ever needs to scan the table as an undifferentiated whole. Unlike `rent_payments` (Module 6 §6.4) or `expenses` (Module 7 §7.6) — both partitioned because their dominant dashboard/reporting queries are genuinely bounded to a recent or fiscal-period date range in addition to a status/category filter — `building_documents` has **no single dominant query that scans across the whole table by date range**: the closest candidate, "Expiring Documents," is already served by a narrow partial index (`idx_building_documents_expiring`) that only ever contains the bounded, near-term-relevant subset of rows with a populated `expiry_date`, not the table's full historical volume. Every other stated access pattern is an FK-equality lookup bounded to one building or one company, the identical shape already excluded from partitioning for `maintenance_request_attachments` (Module 8 §8.6) and `listing_images` (Module 9 §9.5) at comparable-to-larger row-count targets (15,000,000+ and 20,000,000+ respectively). **Recommendation: do not partition `building_documents`.** |

**Should `document_categories` ever be partitioned?** No — at a trivial row count with no unbounded per-entity growth pattern, this question does not meaningfully arise, the same conclusion already reached for every small reference/lookup table in this schema (`company_settings`, `subscription_plans`, `permissions`).

**Should `building_documents` be revisited if this conclusion changes?** If a future compliance-reporting feature introduces a genuinely platform-wide, date-range-bounded scan (e.g., "every document issued this fiscal year, across every company, for a regulator-facing export") as a real, frequent access pattern rather than a rare one-off export, this conclusion should be revisited against `issue_date` or `created_at` — but no such pressure is evident from the stated scale target or the stated Performance requirements (Building Documents, Category Filtering, Expiring Documents, Search, Pagination), all of which are building/company-scoped, not platform-wide-date-range-scoped. This mirrors the identical forward-looking caveat already applied to `efawateercom_transactions` (Module 7 §7.6) and `viewing_requests` (Module 9 §9.5) — flagged as a possibility, not a present need.

## 10.5 Performance Optimization Explanation

- **Building Documents:** `idx_building_documents_building_created` — equality-leading composite with `DESC` trailing sort column, turning the building detail page's documents tab into a single ordered index scan, the standard pattern applied without exception since Module 3.
- **Category Filtering:** `idx_building_documents_building_category` (building-scoped: "just the Insurance documents for this building") and `idx_building_documents_company_category` (portfolio-scoped: "every Insurance document across the whole company") together cover both granularities of the stated requirement, mirroring the identical dual-composite pattern already established for `apartments` (`idx_apartments_building_id` alongside `idx_apartments_company_occupancy`, Module 4 §4.4).
- **Expiring Documents:** `idx_building_documents_expiring` — the narrowest, most surgical partial index in this module, scoped to exactly the subset of rows carrying a populated `expiry_date`, reserved for the single highest-compliance-value, recurring operational query in this table's life (the renewal-reminder sweep), the same narrow-partial-index discipline as `idx_lease_contracts_expiration` (Module 5 §5.1) and `idx_marketplace_listings_expiring` (Module 9 §9.1).
- **Search:** `idx_building_documents_document_name_trgm` — fuzzy substring search on the short document-name field, the same trigram pattern already applied to `buildings.name`, `lease_contracts.contract_number`, `maintenance_requests.title`, and `marketplace_listings.listing_title`.
- **Pagination:** every composite index with a trailing `DESC` column directly supports keyset pagination (`WHERE (building_id, created_at) < ($1, $2) ORDER BY created_at DESC LIMIT 50`), the same preferred-over-`OFFSET` strategy established since Module 3 §3.10 — relevant here given this table's 10,000,000+-row target places it among this schema's larger tables by row count.
- **Category Lookup (for the picker UI):** `document_categories`' own unique constraint on `(company_id, name)` doubles as the "list this company's categories, sorted by name" index, requiring no additional index of its own — a small, low-write, low-query-frequency table by nature.

## 10.6 Security & Multi-Tenant Isolation

- **RBAC:** Document upload, category management, and confidential-document access are gated by existing `documents.upload`/`documents.manage_categories`/`documents.view_confidential`-style permission keys (Module 3, `permissions`) resolved via `role_permissions` — no new RBAC machinery introduced structurally, since this module consumes the existing platform-wide permission catalog exactly as every prior module has; the one addition is a dedicated `documents.view_confidential` permission key specifically gating the confidential-document read path described below, seeded into the permission catalog like any other platform-defined key.
- **Confidential Document Access — the one genuinely novel security mechanism this module introduces (§10.0).** Every prior module's tenant-isolation story is binary: a row is either visible to the owning company's authenticated members (the default) or, in the Marketplace's single deliberate exception, additionally visible to the public (Module 9 §9.7). `building_documents.is_confidential` introduces a third, *intra*-tenant dimension — some rows within the same company must be hidden from *some* of that company's own authenticated staff. Standard row-level `company_id`-scoped RLS cannot express this by itself, since RLS operates on tenant identity, not on a specific authenticated user's role/permission set within that tenant. The layered mechanism:
  - **Primary defense (application/API layer):** every read of `building_documents` filters out `is_confidential = true` rows unless the requesting user's resolved permission set (via `user_company_roles → roles → role_permissions → permissions`, the same resolution path every other authorization check in this schema already uses, Module 3 §3.9/§3.10) includes `documents.view_confidential`. This is the primary, cheap, first line of defense in the common case, consistent with how this schema treats every cross-table or permission-set-dependent invariant that a single-row CHECK/RLS predicate cannot fully express on its own (the maintenance-request status-transition graph, Module 8 §8.1; the marketplace vacancy-publish gate, Module 9 §9.0).
  - **Recommended Phase 8 hardening (database layer):** a DB-level RLS policy of the shape `USING (company_id = current_setting('app.current_company_id')::uuid AND (is_confidential = false OR has_permission(current_setting('app.current_user_id')::uuid, 'documents.view_confidential')))`, where `has_permission(...)` is a `SECURITY DEFINER` SQL function performing the same role-permission resolution — so the confidentiality guarantee holds even against a direct SQL write/read bypassing the application layer, the identical belt-and-suspenders posture already recommended for `lease_contracts` immutability (Module 5 §5.1) and the marketplace vacancy gate (Module 9 §9.0). This is flagged as Phase 8 hardening rather than built as the primary mechanism here because it introduces the first RLS policy in this schema that depends on resolved permission state rather than tenant identity alone — a materially higher-complexity policy shape warranting its own dedicated design pass in Phase 8 rather than being finalized as a byproduct of this module.
  - **Why not a separate confidential-documents table instead:** a structurally separate table (mirroring the `rent_payment_receipts`/`expense_receipts` table-per-type philosophy, Phase 1 §1.20) was considered and rejected — unlike receipts, where the two concrete types are genuinely different business objects with different lifecycles, a confidential and a non-confidential building document are the *same* business object (same categories, same query shapes, same lifecycle) differing only in who may read one specific row at one point in time; splitting the table would duplicate every index and query path in this module for a distinction that is fundamentally a read-access-control concern, not a structural/business-object difference — the identical reasoning that already kept `marketplace_listings`' `INTERNAL`/`EXTERNAL` modes (a genuine structural difference) in one table via a CHECK constraint rather than two tables (Phase 1 §1.24), applied here to an even less structurally different case.
- **Audit Logs:** Every table in this module writes to `audit_logs` on mutation per the Global Convention; `is_confidential` flag changes and any soft-delete on `building_documents` are flagged elevated-severity given their direct effect on who can see a potentially sensitive record.
- **Multi-Tenant Isolation:** Both tables in this module carry a directly-populated `company_id` and are RLS-ready under the standard `USING (company_id = current_setting('app.current_company_id')::uuid)` policy, layered with the confidentiality predicate described above for `building_documents` specifically. Neither table in this module needs the Marketplace's public-read carve-out (Module 9 §9.7) — every row in every table here belongs unambiguously to exactly one company with no legitimate cross-tenant access case, confidential or otherwise.
- **Soft Delete:** Standard across both tables; `building_documents`' soft-delete is deliberately narrow in scope (§10.2), reserved for genuine data-entry error rather than any lifecycle concept tied to document expiry.
- **Evidentiary Integrity:** `building_documents` — carrying ownership deeds, licenses, permits, and insurance documentation — is treated with the same compliance/dispute-prevention seriousness Phase 1 §1.23 originally flagged for this concept: documents are never overwritten in place, only soft-deleted-and-replaced for genuine correction, preserving a complete filing trail for any later regulatory, ownership, or insurance dispute.

## Module 10 (Documents) — Architecture Review

- **PostgreSQL Best Practices:** UUIDv7 PKs throughout; `TIMESTAMPTZ` for all point-in-time audit columns versus correctly-typed `DATE` for calendar-date concepts (`issue_date`, `expiry_date`) — the identical DATE-vs-TIMESTAMPTZ discipline applied correctly and consistently since Module 5. No monetary columns exist in this module, so the `NUMERIC(12,3)`/`currency` convention is not applicable here — correctly absent rather than reflexively included, the same "correctly absent" call already made for Module 8's maintenance tables.
- **Referential Integrity:** Every FK in this module is `NOT NULL` and `RESTRICT`-on-delete for the structural parent-child relationships (`building_id`, `category_id`, `file_id`), except the standard `SET NULL` actor-attribution columns (`created_by`/`updated_by`/`deleted_by`/`uploaded_by`) — consistent with the platform-wide "preserve history, sever only the actor-attribution edge" pattern established in every prior module. This module introduces no nullable structural FK anywhere, the same narrow-scope consequence already noted for Module 9's tables — every document has exactly one building, one category, and one file.
- **Constraint Quality:** The `expiry_date`/`issue_date` ordering constraint was deliberately reviewed against the real-world "many documents never expire at all" case (ownership deeds, signed contracts) and both date columns were left fully nullable and independently unconstrained against `CURRENT_DATE` in the expiry direction specifically because the stated "expired documents remain stored for historical purposes" business rule requires a genuinely valid, unconstrained past-dated `expiry_date` to remain representable — called out explicitly here as a constraint shape that was considered and deliberately left asymmetric (issue date bounded against the future, expiry date not), not applied mechanically the same way in both directions, continuing the "show the caught near-miss / deliberate scoping decision" transparency discipline established in Module 3 §3.5 and continued in Modules 6 and 8.
- **Index Quality:** Every composite index in this module was checked for column-order correctness (equality-before-range/sort, `DESC` embedded where a query needs most-recent-first) — no index found with the wrong leading column. Two indexes were deliberately **not** created and the omission explicitly justified rather than silently skipped: a standalone `is_confidential` index and a standalone `uploaded_by` index (§10.2) — both real candidates a less careful pass might add reflexively, both correctly identified as adding write cost without a corresponding read benefit given this module's actual stated query patterns. A standalone `company_id` index on `document_categories` was also considered and correctly identified as fully redundant with the unique constraint's own backing composite, the same class of caught redundancy already documented for `idx_role_permissions_role_id` (Module 3 §3.5) and `idx_listing_images_listing_display_order` (Module 9 §9.2).
- **Query Performance:** Every stated required query shape (Building Documents, Category Filtering, Expiring Documents, Search, Pagination) is explicitly mapped to a specific index in §10.5, with no requirement left unaddressed and no index added without a corresponding named requirement — the same discipline as Modules 4, 6, 7, 8, and 9's requirement-to-index mapping.
- **Security:** Reviewed against every requirement in the module brief (§10.6) — RBAC, audit logging, multi-tenant isolation, and soft delete all confirmed present and standard-shaped. This module's one genuinely novel security consideration — differentiated, permission-gated read access to confidential rows *within* the same tenant, as opposed to every prior module's binary tenant-isolated-vs-public shape — is addressed with an explicit, layered application-plus-recommended-RLS mechanism rather than either ignoring the requirement's real complexity or over-claiming a single-row CHECK/simple-RLS-predicate solves it, continuing the honest-layered-defense posture already established for over-allocation prevention (Module 6 §6.3) and circular renewal-chain prevention (Module 5 §5.1).
- **Multi-Tenant Isolation:** Confirmed — both tables denormalize/carry `company_id` directly (§10.0, §10.6); neither table in this module needs the Marketplace's public-read carve-out, since building documents (confidential or not) have no legitimate cross-tenant access case.
- **Future Scalability:** `building_documents` was evaluated against partitioning and excluded on the same query-pattern-driven grounds already established for `maintenance_request_attachments` (Module 8 §8.6) and `listing_images` (Module 9 §9.5) — its dominant access patterns are FK-equality lookups bounded to one building or one company, not a platform-wide date-range scan, even accounting for the "Expiring Documents" requirement, which is already served by a narrow partial index rather than needing partition pruning. `document_categories` was correctly identified as trivially small at any realistic scale, requiring no scalability treatment at all.
- **Maintainability:** Every non-obvious modeling decision in this module — the company-scoped-table-not-enum choice for categories, the deliberate absence of a system/custom category split (unlike `roles`), the `uploaded_by`/`created_by` distinction mirrored from `maintenance_request_attachments`, the asymmetric issue/expiry date-constraint treatment, and the layered confidential-document access mechanism — is documented in place with its specific business and technical reasoning, continuing the "no undocumented deviation" discipline maintained without exception since Module 1.
