# MODULE 9 — MARKETPLACE

Continuation of `PropertyOS_Phase3_Physical_Design.md`, `PropertyOS_Module4_Properties.md`, `PropertyOS_Module5_Leasing.md`, `PropertyOS_Module6_RentPayments_Updated.md`, `PropertyOS_Module7_FinancialOperations_Updated.md`, and `PropertyOS_Module8_Maintenance.md`. Applies the same Global Conventions (UUIDv7 PKs, `created_at`/`updated_at`/`created_by`/`updated_by`, soft delete, `company_id` + RLS tenant isolation, `snake_case` naming) unless a deviation is explicitly justified.

Scope for this module is deliberately narrow, per the module brief: **three tables only** — `marketplace_listings`, `listing_images`, `viewing_requests`. No agents, brokers, commissions, chats, negotiations, favorites, ratings, reviews, or analytics — those are explicitly out of scope and are not introduced anywhere below, even implicitly via a stray column.

Scale target for this module: **2,000,000+ listings, 15,000,000+ listing images, 10,000,000+ viewing requests, 10,000+ companies.**

## 9.0 Module-Wide Design Decisions (read before the tables)

**This module implements INTERNAL-mode listings only — a deliberate, explicit narrowing of Phase 1 §1.24's original dual-mode (`INTERNAL`/`EXTERNAL`) conceptual design.** Phase 1 §1.24 originally proposed a `listing_source` enum supporting both PropertyOS-managed units (`INTERNAL`, `apartment_id` mandatory) and externally-owned properties published purely as marketplace distribution (`EXTERNAL`, `apartment_id` NULL, descriptive fields stored directly on the listing row). This module's explicit brief — "Support: Company, Building, Apartment, Listing Title, Listing Description, Monthly Rent, Security Deposit, Currency, Listing Status, Published Date, Expiration Date, Is Featured, Contact Phone, Contact WhatsApp, Created By, Updated By, Soft Delete" — names `apartment_id` as a required, unconditional field with no `listing_source` discriminator and no `external_*` column set. This module's `marketplace_listings` table is therefore built strictly to that field list: `apartment_id` is mandatory and non-nullable, exactly the Phase 1 §1.24 `INTERNAL` case, with no structural provision for an `EXTERNAL` listing. This is documented explicitly, not silently narrowed, so a future module extending the Marketplace to external/non-managed properties has a clear, correctly-scoped starting point (the original Phase 1 §1.24 CHECK-constraint-gated dual-mode design remains the correct blueprint for that future extension — it is not contradicted here, simply not built in this pass since it's outside this module's stated field list).

**Publishing is a gate against `apartments.occupancy_status`, not a state that writes back to it.** Per the stated business rule "Publishing a listing must not change apartment occupancy," `marketplace_listings.status` transitioning to `published` never touches `apartments.occupancy_status` — that column remains driven exclusively by the existence of an *active* `lease_contracts` row, per Module 4 §4.4's trigger-maintained cache. The relationship runs the other direction and only at the moment of transition: the application must verify `apartments.occupancy_status = 'vacant'` **before** permitting a `draft → published` transition (the stated "Only vacant apartments can be published" rule), but that check is a one-time gate at publish-time, not an ongoing synchronization. This keeps the two concepts — marketing/publication state and leasing/occupancy state — cleanly decoupled, exactly as Phase 1 §1.6 already decoupled `occupancy_status` from every other unit-lifecycle concept.

**Lease activation reconciles a published listing to `rented`, for every lease created or activated through PropertyOS.** When a `lease_contracts` row transitions to `status = 'active'`, the same application-orchestrated transaction that performs that activation must also check whether the same `apartment_id` has a `marketplace_listings` row with `status = 'published'`, and if so, transition that listing to `status = 'rented'` within the same transaction — reusing the existing `rented` status value already defined on `listing_status_enum`, with no new table, column, or status introduced. This is the natural, low-cost extension of the "lease creation/activation is a multi-table transaction" pattern already established in Module 5 (renewal, termination), and it closes the reconciliation gap for the case that actually matters operationally: a unit leased through PropertyOS itself, whether via the marketplace inquiry funnel or a staff-initiated lease creation flow entirely independent of it. This workflow is deliberately scoped to leases recorded in PropertyOS — it does not attempt to detect, and structurally cannot detect, a fully external/offline lease that is signed outside the platform and never recorded here at all; a unit taken off the market through such a genuinely unrecorded channel does not automatically un-publish its listing at the database level, and reconciling that narrower remaining edge case (an entirely off-platform walk-in lease) remains an application-layer/scheduled-job concern, not a structural integrity question the schema itself can resolve.

**Why the vacancy gate is application-layer, not a CHECK constraint.** "Only vacant apartments can be published" is a cross-table, cross-value invariant (`marketplace_listings.status = 'published'` correlated against a *different* table's `apartments.occupancy_status` value) — structurally identical in kind to the class of rule this schema has consistently kept at the application layer throughout (`lease_contracts` financial-term immutability, Module 5 §5.1; the maintenance-request status transition graph, Module 8 §8.1), since PostgreSQL CHECK constraints can only inspect the row being written, never a different table's current state. The recommended Phase 8 hardening is the same layered posture used everywhere else in this schema: a `BEFORE UPDATE` trigger on `marketplace_listings` that raises an exception if `NEW.status = 'published'` and the referenced apartment's cached `occupancy_status != 'vacant'`, as a database-level backstop against a direct-write bypass, in addition to the application-layer check that is the primary, cheap, first line of defense in the common case.

**One active published listing per apartment — the direct structural analogue of `uq_lease_contracts_one_active_per_apartment`.** Per the stated business rule "One apartment can have only one active published listing at a time," this module reuses the exact partial-unique-index pattern already established for "exactly one active lease per apartment" (Module 5 §5.1) and "exactly one active subscription per company" (Module 2) — the recurring "at most one active row per resource" shape in this schema, solved identically each time via a partial unique index rather than an application-level check-then-insert, since a partial unique index is enforced atomically by the database with zero race-condition window.

**Archiving preserves history — `archived` is a terminal status value, never a soft-delete.** Per the stated business rule "Archiving a listing must preserve history," `archived` is one of the five closed `listing_status_enum` values, reached from `published`, `rented`, or `expired` via an ordinary status transition — it is emphatically **not** implemented via `deleted_at`. A soft-deleted listing and an archived listing mean two different things in this schema: `deleted_at` is reserved for genuine data-entry errors (a listing created for the wrong apartment, a duplicate publish), exactly the standard soft-delete philosophy applied everywhere else in this schema, while `archived` is a legitimate, historically-meaningful terminal lifecycle state (a listing that served its purpose and is being retired from active marketing) that must remain fully visible in every listing-history and reporting query the same way a `superseded` `lease_contracts` row does (Module 5 §5.1). Collapsing "archived" into soft-delete would incorrectly hide a real historical marketing record behind the same mechanism reserved for correcting mistakes.

**Denormalized `company_id` on every table in this module**, consistent with the module-wide denormalization principle established in Module 4 §4.0, Module 5 §5.0, Module 6 §6.0, and Module 7 §7.0 — `listing_images` and `viewing_requests` both carry `company_id` directly (denormalized from `marketplace_listings.company_id` at write time) so that company-scoped staff worklists and RLS policy evaluation on this module's two child tables never require a join through `marketplace_listings` just to establish tenant scope.

**The Marketplace is this schema's one deliberately cross-tenant, publicly-readable surface — flagged since Phase 1 §1.24 and Phase 2 §2.4.** `marketplace_listings` (and, transitively, `listing_images`, since a public browser must be able to load a published listing's photos) requires a genuinely non-standard RLS policy shape: authenticated company-staff access remains standard tenant-isolated (`company_id = current_setting('app.current_company_id')::uuid`), but an **additional, deliberately permissive public-read carve-out** — `OR (status = 'published' AND deleted_at IS NULL)` for `marketplace_listings`, and the equivalent join-based carve-out for `listing_images` — is required so that anonymous marketplace visitors can browse published listings across every participating company at once, which is the entire product purpose of a marketplace. `viewing_requests`, by contrast, does **not** get a public-read carve-out — a submitted viewing request is company-confidential lead data (the applicant's name/phone/email), and the RLS policy there remains standard tenant-isolated read, with only the *write* (INSERT) path opened to unauthenticated submission at the application/API layer (detailed in §9.7), never a public *read* path. This distinction — public read for listings, public write-only for viewing requests — is the precise, minimal cross-tenant surface this module needs, not a blanket relaxation of tenant isolation across the whole module.

## 9.1 Table: `marketplace_listings`

**Purpose:** A published (or draft, or retired) marketing record for a PropertyOS-managed apartment being offered for rent — the anchor entity for this module and the parent of every image and viewing request below.

**Business Description:** One row per marketing listing for a specific apartment. Captures the commercial terms shown to a prospective tenant (rent, deposit, currency), the listing's own lifecycle independent of the underlying lease lifecycle (draft → published → rented/expired → archived), and the contact channel a prospective tenant uses to reach the company. Every listing traces to exactly one company-managed apartment — per this module's explicit scope (§9.0), there is no externally-owned-property listing mode in this pass.

**Columns:**

| Column Name | PostgreSQL Data Type | Nullable | Default | Description |
|---|---|---|---|---|
| id | UUID | NO | uuid_generate_v7() | Primary key |
| company_id | UUID | NO | — | Owning company (tenant-scope root) — also the accountable/moderatable publishing party for this listing |
| building_id | UUID | NO | — | Denormalized from `apartment_id → floors → buildings`, see §9.0/Module 4 §4.0 — avoids a two-hop join on every building-scoped listing query |
| apartment_id | UUID | NO | — | The specific unit being marketed — mandatory, per this module's INTERNAL-only scope (§9.0); every listing belongs to exactly one apartment |
| listing_title | VARCHAR(255) | NO | — | Short marketing headline, e.g. "Modern 2BR near Abdoun Circle" — displayed on every marketplace card/search result |
| listing_description | TEXT | NO | — | Full marketing description — required; a title-only listing with no description is not a usable public marketing record |
| monthly_rent | NUMERIC(12,3) | NO | — | The advertised monthly asking rent shown to prospective tenants |
| security_deposit | NUMERIC(12,3) | YES | NULL | The advertised security deposit; nullable since some listings defer deposit terms to direct inquiry/negotiation rather than advertising a fixed figure upfront |
| currency | CHAR(3) | NO | 'JOD' | ISO 4217, per Global Convention |
| status | listing_status_enum | NO | 'draft' | `draft` \| `published` \| `rented` \| `expired` \| `archived` — the stated closed status list; see Business Rules for the full transition model |
| published_date | DATE | YES | NULL | The date this listing was first published (first `draft → published` transition); NULL while still in `draft`. Immutable once set — a listing re-published after expiring does **not** overwrite this with a later date, preserving "when did this unit first hit the market" as a stable historical fact (see Check Constraints and Business Rules) |
| expiration_date | DATE | YES | NULL | The date this listing is scheduled to lapse from active publication; nullable — some companies choose not to set an auto-expiry and instead manually manage listing lifecycle |
| is_featured | BOOLEAN | NO | false | Marketplace homepage/search-result pinning flag — a company-purchased or staff-curated promotional placement |
| contact_phone | VARCHAR(20) | NO | — | The phone number a prospective tenant sees and calls — required; a listing with no way to make contact is not a usable public marketing record |
| contact_whatsapp | VARCHAR(20) | YES | NULL | WhatsApp contact number, where different from (or in addition to) `contact_phone`; nullable since not every company/listing offers WhatsApp contact |
| created_at | TIMESTAMPTZ | NO | now() | — |
| updated_at | TIMESTAMPTZ | NO | now() | — |
| created_by | UUID | YES | NULL | — |
| updated_by | UUID | YES | NULL | — |
| deleted_at | TIMESTAMPTZ | YES | NULL | Soft delete — reserved for genuine data-entry error, never for the ordinary `archived` lifecycle terminus, see §9.0 |
| deleted_by | UUID | YES | NULL | — |

**Primary Key:** `id`

**Foreign Keys:**
- `company_id` → `companies(id)` ON DELETE RESTRICT.
- `building_id` → `buildings(id)` ON DELETE RESTRICT.
- `apartment_id` → `apartments(id)` ON DELETE RESTRICT — per Phase 2, listing history retains real marketing/pricing-trend value and is preserved permanently even after the unit is no longer actively marketed.
- `created_by`, `updated_by`, `deleted_by` → `users(id)` ON DELETE SET NULL.

**Unique Constraints:**
- `uq_marketplace_listings_one_active_per_apartment` — **partial unique index** on `(apartment_id)` WHERE `status = 'published' AND deleted_at IS NULL` — the direct physical enforcement of the stated business rule "one apartment can have only one active published listing at a time" (§9.0), the exact structural pattern already used for `uq_lease_contracts_one_active_per_apartment` (Module 5 §5.1) and `uq_company_subscriptions_one_active` (Module 2). This is the single most important constraint in this module.

**Check Constraints:**
- `chk_marketplace_listings_monthly_rent_positive` — `monthly_rent > 0`.
- `chk_marketplace_listings_security_deposit_nonneg` — `security_deposit IS NULL OR security_deposit >= 0`.
- `chk_marketplace_listings_title_not_blank` — `length(btrim(listing_title)) > 0` — mirrors `chk_maintenance_requests_title_not_blank` (Module 8 §8.1); a whitespace-only headline is a real, cheap-to-catch data-entry failure mode, not a hypothetical one.
- `chk_marketplace_listings_published_date_status_consistency` — `(status = 'draft' AND published_date IS NULL) OR (status != 'draft' AND published_date IS NOT NULL)` — the structural implementation of the stated **"Invalid publication dates"** integrity requirement's core case: a listing cannot claim to have been published (or to be in any status reachable only via publication — `rented`/`expired`/`archived`) without a recorded `published_date`, and a still-`draft` listing cannot carry one.
- `chk_marketplace_listings_published_date_not_future` — `published_date IS NULL OR published_date <= CURRENT_DATE` — a listing documents when it actually went live, not a future-scheduling field, the same "historical fact" reasoning applied to `request_date`/`expense_date`/`reading_date` throughout this schema.
- `chk_marketplace_listings_expiration_after_published` — `expiration_date IS NULL OR published_date IS NULL OR expiration_date > published_date` — the structural implementation of the stated **"Invalid expiration dates"** integrity requirement: an expiration date, when set, must lie strictly after the date the listing actually went live; a listing cannot be scheduled to expire before (or the same day as) its own publication.
- `chk_marketplace_listings_contact_phone_not_blank` — `length(btrim(contact_phone)) > 0`.

**Indexes:**
- `uq_marketplace_listings_one_active_per_apartment` (above) — doubles as **the** "current active published listing for apartment X" lookup (`WHERE apartment_id = $1 AND status = 'published'`), the single most frequent query in this module (every apartment detail page's "is this unit currently marketed" check, and the publish-time vacancy/duplicate-listing gate itself). Preferred over a plain composite index for the identical reason given for its `lease_contracts` counterpart (Module 5 §5.1): it is simultaneously the integrity constraint *and* the performance index, with zero risk of the two drifting out of sync.
- `idx_marketplace_listings_public_published_featured` composite on `(status, is_featured DESC, published_date DESC)` WHERE `status = 'published' AND deleted_at IS NULL` — **the** public-facing **Marketplace Search**/browse query: the marketplace homepage and default search-result ordering ("published listings, featured ones first, then most recently published"). `status` leads (though a constant under this partial index's own `WHERE` clause, it is included so the index is usable for the exact predicate the query issues) with `is_featured DESC` next since featured placement is the marketplace's primary sort dimension by product design, `published_date DESC` trailing as the tiebreak/secondary sort — this turns the single highest-traffic, fully public, cross-tenant query in this module into one ordered index scan with zero separate sort step.
  - *Queries served:* `SELECT * FROM marketplace_listings WHERE status = 'published' AND deleted_at IS NULL ORDER BY is_featured DESC, published_date DESC LIMIT 50` (marketplace homepage, default search ordering, paginated).
  - *Expected improvement:* without this index, the public marketplace's own landing/search view — evaluated on effectively every anonymous visitor's page load, the highest-QPS read path this module has — would sequential-scan a table headed toward 2,000,000 rows; with it, it's a direct ordered index range-scan bounded to the (much smaller, at any given time) currently-published subset.
  - *Why preferred over separate `status`/`is_featured`/`published_date` indexes:* identical composite-over-separate-single-column reasoning established since Module 3 — one structure serves the equality filter and both sort dimensions together, avoiding a bitmap-AND-then-sort plan.
- `idx_marketplace_listings_company_status` composite on `(company_id, status)` WHERE `deleted_at IS NULL` — the primary **Company Listings** requirement: a company's own listing-management dashboard, filterable by status ("show my drafts," "show my active listings," "show what's expired"). `company_id` leads as the mandatory tenant-scoping equality filter for every staff-facing (non-public) screen in this module; `status` second as the near-universal secondary equality filter.
- `idx_marketplace_listings_building_status` composite on `(building_id, status)` WHERE `deleted_at IS NULL` — the stated **Building Listings** requirement: a building detail page's "marketplace activity for this building" tab, spanning every unit in it.
- `idx_marketplace_listings_apartment_history` composite on `(apartment_id, published_date DESC)` WHERE `deleted_at IS NULL` — the stated **Apartment Listings** requirement: a unit's full marketing history across its life (multiple listings over time as tenancies turn over) — distinct from the active-listing partial unique index above, which deliberately excludes every non-`published` row; this one must also surface historical `expired`/`archived`/`rented` listings for the unit, the same "active lookup vs. full history needs two different indexes" pattern already established for `idx_lease_contracts_apartment_history` alongside `uq_lease_contracts_one_active_per_apartment` (Module 5 §5.1).
- `idx_marketplace_listings_title_trgm` — GIN trigram index on `listing_title` — supports the stated **Search** requirement, both the public marketplace's own free-text search box and staff searching their own listing inventory by partial/misremembered title, the same trigram-search rationale class as `idx_buildings_name_trgm` (Module 4), `idx_lease_contracts_contract_number_trgm` (Module 5), and `idx_maintenance_requests_title_trgm` (Module 8). **Not** made partial on `status = 'published'` — unlike the browse index above, search must also let staff find their own draft/archived listings by title, so this index intentionally covers the full (non-deleted) row set rather than only the publicly-browsable subset.
- `idx_marketplace_listings_expiring` composite on `(company_id, expiration_date)` WHERE `status = 'published' AND expiration_date IS NOT NULL AND deleted_at IS NULL` — supports a "listings expiring soon" operational worklist/scheduled-job shape (the `published → expired` transition job's own daily sweep, and a company dashboard widget), the identical narrow-partial-index pattern already used for `idx_lease_contracts_expiration` (Module 5 §5.1) and `idx_maintenance_requests_company_open_priority` (Module 8 §8.1) — reserved for exactly the currently-active, date-bounded subset rather than the full historical row set.

**Deliberately omitted indexes:**
- No standalone `is_featured` index outside the public-browse composite above — featured-only filtering independent of the `published` status scope is not a stated query requirement, and the composite already serves the one realistic featured-listing access pattern.
- No index on `monthly_rent`/`security_deposit`. Rent-range filtering ("show listings between 300–500 JOD") is a real marketplace feature in spirit but was not named as a stated required query shape in this module's brief, and adding a range index speculatively — beyond the stated Performance requirements list — would violate the "avoid unnecessary indexes" instruction repeated throughout this schema's briefs; if a concrete rent-range filter requirement is added in a future pass, a B-tree on `(status, monthly_rent) WHERE status='published'` is the natural, cheap addition at that time.
- No index on `listing_description` beyond the `listing_title` trigram — identical reasoning to `maintenance_requests.description`'s omission (Module 8 §8.1): `listing_title` is this table's short, purpose-built summary field, and a second GIN index on the long-form description would be write-amplification for marginal search-quality gain.
- No standalone `contact_phone`/`contact_whatsapp` index — these are display/contact fields, never a stated lookup dimension ("find the listing with this contact number" is not a realistic product query).

**Business Rules:**
- **Status transition model:** `draft → published` (gated by the vacancy check, §9.0); `published → rented` (the unit is taken off active marketing because a lease was signed through PropertyOS — per §9.0, this transition is mandatory and application-orchestrated, fired in the same transaction as the corresponding `lease_contracts` row's transition to `status = 'active'` for the same apartment, though the two remain structurally independent tables); `published → expired` (automated, via the scheduled job comparing `expiration_date` against `CURRENT_DATE`, or manual staff action); `rented → archived`, `expired → archived`, or directly `published → archived` (manual staff retirement of a listing that's served its purpose) — every terminal path converges on `archived` without ever passing through soft-delete, per §9.0. A `draft` listing may also be soft-deleted directly (an abandoned, never-published draft) — the one legitimate case where soft-delete applies to a listing that never reached a "real" public-facing state.
- The full state-transition **graph** (disallowing, say, a jump directly from `archived` back to `published` without an explicit, deliberate re-listing action, or from `draft` directly to `rented`) is an application-layer workflow guard, not a DB constraint — identical reasoning and identical recommended Phase 8 hardening posture (a `BEFORE UPDATE` trigger validating `OLD.status → NEW.status` against an allowed-transitions table) already established for `maintenance_requests.status` (Module 8 §8.1) and `cheque_details.status` (Module 6 §6.2). What *is* enforced today at the DB level is the narrower, stateless, single-row-checkable invariant (`published_date` presence/absence matching draft-vs-published-or-later status), the same class of rule a CHECK constraint *can* express.
- `apartment_id`/`building_id`, once set, are immutable — a listing is created for a specific unit and is never administratively reassigned to a different apartment; a listing for the wrong unit is a data-entry error corrected by soft-deleting the mistaken row and creating a new one, not by repointing the FK, consistent with the "denormalized-at-write, immutable thereafter" treatment already given to genuinely structural FKs elsewhere in this schema (e.g. `rent_payments.lease_contract_id`, Module 6 §6.1).
- The vacancy gate ("only vacant apartments can be published") and the "publishing does not change occupancy" non-effect, along with the lease-activation-to-`rented` reconciliation workflow, are all detailed fully in §9.0.

**Soft Delete Strategy:** Standard, but narrow in scope per §9.0 — reserved for genuine data-entry errors (a listing created against the wrong apartment, a duplicate draft), never for the ordinary end-of-life of a real listing, which is expressed via `status = 'archived'`, not deletion.

**Audit Requirements:** Every mutation logged to `audit_logs`; `status` transitions, `monthly_rent`/`security_deposit` changes, and any `deleted_at` soft-delete are treated as elevated-severity events given their public-facing commercial and moderation weight — a change to advertised rent on a public listing, or a listing's removal, is exactly the kind of tenant-facing commercial action this schema's audit posture exists to make traceable.

**Future Scalability Notes:** Explicitly named in the scale target (2,000,000+ rows). Evaluated against, and excluded from, partitioning — full reasoning in §9.5.

## 9.2 Table: `listing_images`

**Purpose:** Supports multiple ordered photographs per marketplace listing, integrating with the central `file_storage` governance table — the visual content that is, in practice, the single highest-influence factor on a prospective tenant's decision to inquire.

**Business Description:** A marketing listing is rarely a single photo — a typical listing carries anywhere from a handful to a couple dozen images (living areas, bedrooms, kitchen, bathroom, building exterior, view). This table is the ordered, cover-flagged image set for one listing.

**Columns:**

| Column Name | PostgreSQL Data Type | Nullable | Default | Description |
|---|---|---|---|---|
| id | UUID | NO | uuid_generate_v7() | Primary key |
| company_id | UUID | NO | — | Denormalized tenant scope, see §9.0 |
| listing_id | UUID | NO | — | The listing this image belongs to — every image belongs to exactly one listing (stated requirement) |
| file_id | UUID | NO | — | FK to `file_storage` — the actual uploaded image metadata/blob pointer |
| display_order | SMALLINT | NO | — | Explicit sort position within the listing's image gallery (0-based); the structural implementation of the stated **"Display Order"** field and the mechanism the public gallery/carousel renders images by |
| is_cover | BOOLEAN | NO | false | Marks the single image used as the listing's primary thumbnail on marketplace cards/search results — the stated **"Is Cover Image"** field |
| uploaded_by | UUID | YES | NULL | FK to `users`; nullable for system-migrated/bulk-imported historical images |
| created_at | TIMESTAMPTZ | NO | now() | — |
| updated_at | TIMESTAMPTZ | NO | now() | — |
| created_by | UUID | YES | NULL | — |
| updated_by | UUID | YES | NULL | — |
| deleted_at | TIMESTAMPTZ | YES | NULL | Soft delete |
| deleted_by | UUID | YES | NULL | — |

**Primary Key:** `id`

**Foreign Keys:**
- `company_id` → `companies(id)` ON DELETE RESTRICT.
- `listing_id` → `marketplace_listings(id)` ON DELETE RESTRICT — per the stated **"Orphan images"** integrity requirement; an image can never exist without a valid owning listing.
- `file_id` → `file_storage(id)` ON DELETE RESTRICT — the file metadata record must outlive this join row, identical reasoning to `contract_documents.file_id` (Module 5 §5.5), `maintenance_request_attachments.file_id` (Module 8 §8.2), and every other `file_storage`-integrated table in this schema.
- `uploaded_by`, `created_by`, `updated_by`, `deleted_by` → `users(id)` ON DELETE SET NULL.

**Unique Constraints:**
- `uq_listing_images_listing_display_order` on `(listing_id, display_order)` WHERE `deleted_at IS NULL` — the direct structural implementation of the stated **"Duplicate image order inside one listing"** integrity requirement: two images on the same listing can never claim the same gallery position, eliminating any ambiguity in render order at the database level rather than leaving it to be silently tolerated (and inconsistently resolved by whatever the application's default secondary sort happens to be) by application code alone.
- `uq_listing_images_one_cover` — **partial unique index** on `(listing_id)` WHERE `is_cover = true AND deleted_at IS NULL` — the direct structural implementation of the stated **"Multiple cover images for one listing"** integrity requirement, using the identical partial-unique-index "at most one flagged row per parent" pattern already established for `uq_parking_assignments_active_spot` (Module 4 §4.6), `uq_lease_contracts_one_active_per_apartment` (Module 5 §5.1), and `uq_marketplace_listings_one_active_per_apartment` (§9.1 above) — atomically enforced by the database, zero race-condition window.

**Check Constraints:**
- `chk_listing_images_display_order_nonneg` — `display_order >= 0`.

**Indexes:**
- `idx_listing_images_listing_display_order` on `(listing_id, display_order)` WHERE `deleted_at IS NULL` — **the** query this table exists to serve, and the stated **Image Loading** performance requirement directly: "load this listing's full image gallery, in display order" — both the listing detail page and, transitively, the public marketplace card's thumbnail lookup. Implemented as a composite so the equality filter (`listing_id = $1`) and the mandatory display-order sort are served by a single ordered index scan with zero separate sort step, identical to the `(building_id, floor_number)` pattern established for `idx_floors_building_id` (Module 4 §4.3). This index and the `uq_listing_images_listing_display_order` unique constraint above cover the identical column set — PostgreSQL will use the unique index's own backing B-tree for this exact query shape, meaning **no separate index is actually created**; this is called out explicitly here (rather than silently shipping a redundant second index) for the identical "avoid unnecessary indexes, catch the redundancy" discipline already demonstrated for `idx_role_permissions_role_id` (Module 3 §3.5).
- `uq_listing_images_one_cover` (above) — doubles as the "get this listing's cover image" lookup (`WHERE listing_id = $1 AND is_cover = true`), the marketplace search-result card's single-image-per-card query — a real, extremely high-frequency read (evaluated on every card rendered in every public search-result page), efficiently served by this partial index's own backing structure without a dedicated additional index.

**Deliberately omitted index:** no standalone `file_id` index — "which listing does this file belong to" has no realistic reverse-lookup product feature, the identical reasoning already applied to `contract_documents` (Module 5 §5.5), `expense_receipts` (Module 7 §7.2), and `maintenance_request_attachments` (Module 8 §8.2); a data-integrity audit, if ever needed, tolerates a sequential scan against this table's modest per-listing row count.

**Business Rules:** Changing which image is the cover is a two-step operation within a single transaction (unset the currently-`true` row's `is_cover` to `false`, then set the newly-chosen row's `is_cover` to `true`) — necessary specifically *because* `uq_listing_images_one_cover` is a hard, immediately-enforced constraint with no deferred-checking window: attempting to set a new cover before clearing the old one within the same statement would violate the constraint. This is application-orchestrated, mirroring how every other "change which row holds an exclusive flag" operation in this schema (e.g., a parking-spot reassignment ending the old `parking_assignments` row before a new one is created, Module 4 §4.6) is handled as an explicit multi-step transaction rather than a single blind UPDATE. `display_order` values are re-sequenced by the application whenever an image is inserted, removed, or manually reordered (typically a full re-write of the affected listing's `display_order` values in one transaction) — not maintained by a DB trigger, since reordering is a direct user-driven UI action (drag-and-drop reordering) rather than a value derivable from another table's state.

**Soft Delete Strategy:** Standard — a superseded/incorrect image (wrong photo uploaded, a photo the company wants removed) is soft-deleted and, if replaced, a new row is created rather than the file being overwritten in place, preserving the historical listing-content trail, identical philosophy to `contract_documents` (Module 5 §5.5) and `maintenance_request_attachments` (Module 8 §8.2).

**Audit Requirements:** Standard `audit_logs` coverage; upload, cover-image changes, and soft-delete events are all logged, since altering a public-facing marketing asset is a traceable action with real commercial/moderation weight.

**Future Scalability Notes:** Explicitly named in the scale target (15,000,000+ rows). Evaluated against, and excluded from, partitioning — full reasoning in §9.5; its dominant query pattern is the FK-equality lookup above, not a time-range scan, the identical shape and conclusion already reached for `maintenance_request_attachments` (Module 8 §8.6) and the Module 7 receipt tables.

## 9.3 Table: `viewing_requests`

**Purpose:** Captures a prospective tenant's request to view a marketplace-listed unit — the top of the tenant-acquisition funnel, and the one entity in this module explicitly designed for **unauthenticated public submission**.

**Business Description:** A visitor browsing the public marketplace who wants to see a unit in person submits their own name and contact details directly against a specific listing, without needing (or being asked for) a `users` account or an existing `tenants` record — friction-minimization matters for lead conversion, per Phase 1 §1.26's explicit design intent. Staff then work the request through a simple, explicit lifecycle (contacted → scheduled → completed, or cancelled) as an operational lead-management worklist.

**Note on scope relative to Phase 1 §1.26:** Phase 1's conceptual description allowed for an optional link from a viewing request forward into a `tenants` row (the requester "may not yet exist as a `tenants` row — they're a lead, not a signed tenant"). This module's explicit field list — Listing, Applicant Name, Phone Number, Email, Preferred Viewing Date, Notes, Request Status, Submitted At — does not include a `tenant_id` (or `user_id`) column, so this table captures only the applicant's directly-supplied contact information as free-standing fields, with no structural link to `tenants`/`users` for the requester side. This is a deliberate scope decision matching this module's stated brief, not an oversight; a future pass linking a converted lead to its eventual `tenants` row (once/if that visitor actually signs a lease) is a clean additive extension — a nullable `tenant_id` FK added later — requiring no change to this table's existing columns.

**Columns:**

| Column Name | PostgreSQL Data Type | Nullable | Default | Description |
|---|---|---|---|---|
| id | UUID | NO | uuid_generate_v7() | Primary key |
| company_id | UUID | NO | — | Denormalized from the parent listing's `company_id`, see §9.0 — the accountable/managing party who must work this lead |
| listing_id | UUID | NO | — | The listing this viewing request concerns — every request belongs to exactly one listing (stated requirement) |
| applicant_name | VARCHAR(255) | NO | — | The prospective tenant's self-reported full name — required; an anonymous, unnamed request gives staff nothing to act on |
| phone_number | VARCHAR(20) | NO | — | Required primary contact channel — a viewing request with no way to reach the applicant back is not actionable |
| email | VARCHAR(255) | YES | NULL | Optional secondary contact channel — the stated **"Email (optional)"** field; many Jordanian marketplace visitors provide phone only |
| preferred_viewing_date | DATE | YES | NULL | The applicant's requested viewing date; nullable since a visitor may submit a general interest request without a specific preferred date ("anytime this week") |
| notes | TEXT | YES | NULL | Free-form applicant-supplied context (e.g., "available evenings only," "interested if pet-friendly") or staff-added follow-up notes |
| request_status | viewing_request_status_enum | NO | 'pending' | `pending` \| `contacted` \| `scheduled` \| `completed` \| `cancelled` — the stated closed status list |
| submitted_at | TIMESTAMPTZ | NO | now() | The moment the request was received — the stated **"Submitted At"** field; doubles as the Global Convention's own `created_at` semantics for this specific business-meaningful timestamp (see Business Rules) |
| created_at | TIMESTAMPTZ | NO | now() | — |
| updated_at | TIMESTAMPTZ | NO | now() | — |
| created_by | UUID | YES | NULL | NULL for the overwhelming majority of rows — genuinely public, unauthenticated self-submissions have no `users` actor; populated only when staff manually log a request on the applicant's behalf (e.g., a phone-in inquiry) |
| updated_by | UUID | YES | NULL | — |
| deleted_at | TIMESTAMPTZ | YES | NULL | Soft delete |
| deleted_by | UUID | YES | NULL | — |

**Primary Key:** `id`

**Foreign Keys:**
- `company_id` → `companies(id)` ON DELETE RESTRICT.
- `listing_id` → `marketplace_listings(id)` ON DELETE RESTRICT — per the stated **"Orphan viewing requests"** integrity requirement; a request can never exist without a valid owning listing, and the listing itself is preserved permanently as lead-generation/funnel-analytics evidence per Phase 2's relationship catalog (§2.1.G).
- `created_by`, `updated_by`, `deleted_by` → `users(id)` ON DELETE SET NULL.

**Unique Constraints:** None. Two distinct viewing requests for the same listing from the same phone number are **not** rejected — a genuine returning-interest visitor (asked to view once, circumstances changed, wants to view again later) is not a duplicate error, and a hard uniqueness constraint on `(listing_id, phone_number)` would incorrectly block this legitimate re-inquiry; the same "don't over-constrain a real-world repeatable event" reasoning already applied to `expenses` (Module 7 §7.1) having no natural business key.

**Check Constraints:**
- `chk_viewing_requests_applicant_name_not_blank` — `length(btrim(applicant_name)) > 0`.
- `chk_viewing_requests_phone_not_blank` — `length(btrim(phone_number)) > 0`.
- `chk_viewing_requests_preferred_date_not_before_submission` — `preferred_viewing_date IS NULL OR preferred_viewing_date >= submitted_at::date` — a visitor cannot request a viewing for a date before they even submitted the request; guards against an obvious data-entry/date-picker error without over-constraining legitimate near-term or open-ended requests.

**Indexes:**
- `idx_viewing_requests_listing_submitted_at` composite on `(listing_id, submitted_at DESC)` WHERE `deleted_at IS NULL` — the primary **Viewing Request Management** query: "full request history for this listing, most-recent-first," the listing detail page's leads tab. `listing_id` leads as the mandatory equality filter; `submitted_at DESC` trails so the common "most recent inquiries first" access is a direct ordered index scan, the same trailing-`DESC` composite pattern established throughout this schema.
- `idx_viewing_requests_company_status_submitted_at` composite on `(company_id, request_status, submitted_at DESC)` WHERE `deleted_at IS NULL` — the company-wide operational worklist: "all viewing requests for company X in status Y, most recent first" — the leads-management dashboard's default view. `company_id` leads for tenant scope, `request_status` second as the near-universal secondary equality filter (staff triage one status bucket at a time, most commonly `pending`), `submitted_at DESC` trailing for recency ordering — the identical shape and rationale as `idx_maintenance_requests_company_status_request_date` (Module 8 §8.1).
- `idx_viewing_requests_company_pending` composite on `(company_id, submitted_at DESC)` WHERE `request_status = 'pending' AND deleted_at IS NULL` — a deliberately narrower, partial-on-status companion index purpose-built for the single highest-frequency screen in this table's operational life: the "new leads awaiting first contact" worklist every leasing agent checks first each day. This mirrors the exact `idx_maintenance_requests_company_open_priority` (Module 8 §8.1) / `idx_rent_payments_late_overdue` (Module 6 §6.1) pattern of a narrow, single-purpose partial index reserved for the one query that matters most operationally — because this index only ever contains currently-unworked requests (a small, bounded fraction of total historical request volume at any given time, since most requests move on to `contacted`/`scheduled`/`completed`/`cancelled` and drop out), it stays small and fast indefinitely regardless of how large the table's full historical row count grows.

**Deliberately omitted indexes:**
- No standalone `phone_number`/`email` index — "find all requests from this phone number/email" is not a stated required query shape, and adding a lookup index for it would be reflexive rather than requirement-driven; if a future fraud/spam-detection feature needs it, a partial or trigram index can be added then against a concrete query.
- No standalone `listing_id`-only index — the `(listing_id, submitted_at DESC)` composite above already serves every realistic listing-scoped access pattern as a leftmost-prefix match, so a separate single-column index would be purely redundant, the identical "composite already covers the leftmost-prefix case" reasoning applied to `idx_role_permissions_role_id`'s removal (Module 3 §3.5).

**Business Rules:** `created_by` is NULL for the overwhelming majority of rows by design — a genuinely public, unauthenticated visitor submitting a viewing request has no `users` row to attribute the INSERT to, which is the entire point of this table existing as a low-friction, account-free entry point (Phase 1 §1.26). `submitted_at` is set once at creation and never updated thereafter, remaining the authoritative "when did this lead first arrive" fact even as `request_status` and `notes` are updated by staff working the lead over subsequent days. Status transitions (`pending → contacted → scheduled → completed`, or a diversion to `cancelled` from any non-terminal state) are staff-driven, ordinary application-layer UPDATEs — this table's lifecycle is materially simpler than `maintenance_requests`'/`cheque_details`' state machines (no date/reason-field correlation requirements were stated for this table), so no dedicated status-history child table or per-status CHECK-constraint gate was introduced here; adding one would be speculative machinery beyond what this module's stated brief actually asks for.

**Soft Delete Strategy:** Standard — reserved for genuine spam/erroneous submissions (a bot-submitted or clearly fraudulent request) and for a rare admin-driven privacy-erasure request from the applicant themselves (a real PDPL consideration for public-facing personal-data collection, per Phase 1's PDPL framing for `audit_logs`); a real, legitimately-submitted lead is never soft-deleted merely because it didn't convert, since `cancelled`/`completed` already correctly capture "this lead is closed out" without destroying the funnel-analytics record.

**Audit Requirements:** Standard `audit_logs` coverage; status transitions and soft-deletes are logged, since altering or removing lead data is a traceable action, though at standard (not elevated) severity — unlike a financial or legal record, a viewing request's operational weight is real but comparatively low-stakes, consistent with how this schema calibrates severity to actual consequence rather than applying `critical`/high-severity uniformly.

**Future Scalability Notes:** Explicitly named in the scale target (10,000,000+ rows). Evaluated against, and excluded from, partitioning — full reasoning in §9.5; dominant query pattern is the FK-equality-lookup-and-sort composite above, bounded per-listing/per-company, the identical shape already established for `maintenance_request_comments` (Module 8 §8.6).

## 9.4 Database Integrity Summary

| Risk | Prevention Mechanism | Explanation |
|---|---|---|
| Multiple active listings for the same apartment | `uq_marketplace_listings_one_active_per_apartment` partial unique on `(apartment_id) WHERE status='published'` | Atomically enforced at INSERT/UPDATE time — no race-condition window, the identical pattern already validated for `lease_contracts`/`company_subscriptions` |
| Publishing a non-vacant apartment | Application-layer gate checking `apartments.occupancy_status = 'vacant'` before permitting `draft → published`; DB-trigger hardening recommended for Phase 8 | A cross-table invariant a single-row CHECK constraint structurally cannot express; the identical layered posture already applied to `maintenance_requests`'/`cheque_details`' transition-graph rules |
| Duplicate image display order inside one listing | `uq_listing_images_listing_display_order` on `(listing_id, display_order)` | No two images on the same listing can claim the same gallery position |
| Multiple cover images for one listing | `uq_listing_images_one_cover` partial unique on `(listing_id) WHERE is_cover=true` | At most one image per listing can be flagged as the cover, atomically enforced |
| Orphan images (dangling `listing_id` or `file_id`) | `listing_images.listing_id` and `.file_id` both `NOT NULL` with real FKs, `ON DELETE RESTRICT` | No image can exist without valid, permanent references to both its owning listing and its underlying file |
| Orphan viewing requests | `viewing_requests.listing_id` `NOT NULL` with a real FK, `ON DELETE RESTRICT` | No viewing request can exist without a valid owning listing |
| Invalid publication dates | `chk_marketplace_listings_published_date_status_consistency`, `chk_marketplace_listings_published_date_not_future` | A listing cannot claim a publication date while still `draft`, cannot omit one once published-or-later, and cannot be dated into the future |
| Invalid expiration dates | `chk_marketplace_listings_expiration_after_published` | An expiration date, when set, must fall strictly after the listing's own publication date |
| Blank/meaningless listing title, description gap, or contact phone | `chk_marketplace_listings_title_not_blank`, `chk_marketplace_listings_contact_phone_not_blank`, `listing_description`/`contact_phone` both `NOT NULL` | Whitespace-only or missing values on public-facing fields carry no marketing value and almost always indicate a client-side submission bug |
| Viewing request with a preferred date before its own submission | `chk_viewing_requests_preferred_date_not_before_submission` | Guards against an obvious date-picker/data-entry error |
| Negative or invalid monetary figures | `chk_marketplace_listings_monthly_rent_positive`, `chk_marketplace_listings_security_deposit_nonneg` | Every monetary column carries an explicit sign constraint matched to its actual valid domain |

## 9.5 Scalability at Target Scale

| Scale point | Impact |
|---|---|
| 10,000 companies | Trivial for every table in this module — per-company row counts stay in the low hundreds to low thousands even at full portfolio size, well within any single index's efficient range. |
| 2,000,000 marketplace_listings | Comfortably single-table. Unlike `rent_payments` (Module 6 §6.4) and `expenses` (Module 7 §7.6), this table's single highest-traffic query — the public marketplace browse/search shape (`idx_marketplace_listings_public_published_featured`) — is a **status-and-featured-flag-bounded** query, not a date-range-bounded one: a listing published a year ago and still `published` today is exactly as relevant to this query as one published this morning. A `published_date`-RANGE partition would not prune anything for the query that actually dominates this table's read load, the identical "the dominant query's date-boundedness assumption does not hold here" reasoning already reached for `maintenance_requests` (Module 8 §8.0/§8.6). **Partitioning is not recommended.** The composite indexes keyed on the table's actual filter columns (`status`, `is_featured`, `company_id`, `building_id`, `apartment_id`) are the correct scaling mechanism. |
| 15,000,000 listing_images | Scales as a small multiple of listings (typically 5–15 images per active listing). Dominant query pattern is a single FK-equality-lookup-and-sort (`idx_listing_images_listing_display_order`), bounded per-listing to a small result set regardless of the table's total row count — the identical shape already excluded from partitioning for `maintenance_request_attachments` (Module 8 §8.6) and the Module 7 receipt tables. **Partitioning is not recommended.** |
| 10,000,000 viewing_requests | Scales independently of `marketplace_listings`' own row count (driven by visitor interest volume, not listing count directly) but remains dominated by the same FK-equality-lookup-and-sort access shape (`idx_viewing_requests_listing_submitted_at`, `idx_viewing_requests_company_status_submitted_at`), bounded per-listing/per-company rather than requiring a platform-wide time-range scan. **Partitioning is not recommended** at the stated target scale; should this table's growth rate ever significantly outpace `marketplace_listings`' own growth (e.g., a viral listing generating disproportionate inbound interest, or a future high-volume lead-generation integration), this conclusion should be revisited against `submitted_at`, mirroring the identical forward-looking caveat already applied to `efawateercom_transactions` (Module 7 §7.6) — but no such pressure is evident from the stated scale target. |

**Should any table in this module be partitioned?** No. `marketplace_listings`, despite reaching a row count in the same order of magnitude as tables partitioned elsewhere in this schema, is explicitly evaluated *against* partitioning on query-pattern grounds — its dominant access pattern is a status/feature-flag filter spanning the table's entire history, not a bounded recent-date-range scan, so a date-based RANGE partition would not serve its real workload, the same conclusion-by-the-same-test already reached for `apartments` (Module 4 §4.4), `lease_contracts` (Module 5 §5.8), and `maintenance_requests` (Module 8 §8.6). The two child tables scale in lockstep with their respective parents (`listing_images` with `marketplace_listings`, `viewing_requests` more loosely with visitor interest) at FK-equality-lookup-dominant access patterns, the same "row count alone doesn't justify it" test already applied consistently since Module 6.

## 9.6 Performance Optimization Explanation

- **Published Listings / Public Listing Search:** `idx_marketplace_listings_public_published_featured` — the narrowest, most surgical partial index in this module, scoped to exactly the publicly-browsable subset and ordered for the marketplace's actual featured-then-recency sort, reserved for the single highest-QPS, fully public query this module serves.
- **Company Listings:** `idx_marketplace_listings_company_status` — equality-leading composite, the standard tenant-scoped staff-dashboard pattern applied throughout this schema.
- **Building Listings:** `idx_marketplace_listings_building_status` — identical pattern, rooted at the building rather than the company.
- **Apartment Listings:** `idx_marketplace_listings_apartment_history` — identical pattern, rooted at the apartment, distinct from the active-only partial unique index since this one must also surface historical rows.
- **Search:** `idx_marketplace_listings_title_trgm` — fuzzy substring search on the short marketing headline, the same trigram pattern already applied to `buildings.name`, `lease_contracts.contract_number`, `expenses.vendor_name`, and `maintenance_requests.title`.
- **Image Loading:** `idx_listing_images_listing_display_order` (via the `uq_listing_images_listing_display_order` unique constraint's backing index) — the single, sufficient index for this table's one realistic access pattern, an ordered per-listing gallery fetch.
- **Viewing Request Management:** `idx_viewing_requests_listing_submitted_at` (per-listing lead history) and `idx_viewing_requests_company_status_submitted_at` / `idx_viewing_requests_company_pending` (company-wide triage worklists, the latter narrowly scoped to the single highest-frequency "new leads" screen) together cover every stated lead-management access shape.
- **Filtering:** every filtering dimension named in the brief (listing status, company, building, apartment, featured flag, viewing-request status) is covered by one of the composite indexes above — no filtering requirement in this module lacks a matching leading-column-correct index.
- **Pagination:** every composite index with a trailing `DESC` sort column directly supports keyset pagination (`WHERE (is_featured, published_date) < ($1, $2) ORDER BY is_featured DESC, published_date DESC LIMIT 50`), the same preferred-over-`OFFSET` strategy established since Module 3 §3.10 — essential here given `listing_images` and `viewing_requests` are, after `meter_readings` and this schema's various history/log tables, among the fastest-growing tables in the schema by row count.
- **Public/Cross-Tenant Read Path:** unlike every prior module, this module's single most-hit index (`idx_marketplace_listings_public_published_featured`) is evaluated by **anonymous, unauthenticated traffic**, not authenticated tenant-scoped staff — flagged explicitly here as the first genuinely public-facing hot path in this schema's indexing story, distinct in kind (not just in RLS shape, §9.7) from every other module's read patterns.

## 9.7 Security & Multi-Tenant Isolation

- **RBAC:** Listing creation, publication, and image management are gated by existing `marketplace.create`/`marketplace.publish`/`marketplace.manage_images`-style permission keys (Module 3, `permissions`) resolved via `role_permissions` — no new RBAC machinery introduced in this module; it consumes the existing platform-wide permission catalog exactly as every prior module has. Viewing-request status management (staff working a lead) is gated by a `marketplace.manage_leads`-style key.
- **Audit Logs:** Every table in this module writes to `audit_logs` on mutation per the Global Convention; `marketplace_listings.status` transitions (especially `draft → published`, a public-visibility event) and `monthly_rent`/`security_deposit` changes are flagged elevated-severity given their public-facing commercial weight.
- **Multi-Tenant Isolation — the one deliberately non-standard RLS shape in this module (§9.0):** `marketplace_listings` requires a policy of the shape `USING (company_id = current_setting('app.current_company_id')::uuid OR (status = 'published' AND deleted_at IS NULL))` — standard tenant-isolated read/write for authenticated company staff, **plus** an explicit, deliberately narrow public-read carve-out limited strictly to the `published` subset, so the platform's anonymous marketplace-browsing surface can function at all. `listing_images` requires the equivalent join-based carve-out (`EXISTS (SELECT 1 FROM marketplace_listings ml WHERE ml.id = listing_images.listing_id AND ml.status = 'published' AND ml.deleted_at IS NULL)` alongside the standard `company_id` clause), since a public visitor viewing a published listing must also be able to load its photos. `viewing_requests` is **not** given a public-read carve-out — its RLS policy remains standard tenant-isolated read only; the public-facing surface for this table is a write-only (INSERT) API path at the application layer, never a read path, keeping applicant contact details (name/phone/email) company-confidential exactly as any other lead-generation data would be. This mirrors and physically implements the exact cross-tenant exception Phase 1 §1.24 and Phase 2 §2.4 (item 2 under "Scalability concerns") already flagged conceptually: `marketplace_listings` is confirmed here as the single highest-scrutiny table in the schema from a security-review standpoint, since any future column added to it must be evaluated for whether it's safe to expose to anonymous/public read — a review discipline explicitly called out here for any future maintainer extending this table.
- **Public Submission Without Authentication:** `viewing_requests` INSERT is intentionally reachable without an authenticated `users` session — enforced at the API/application layer (a dedicated, rate-limited, unauthenticated public endpoint), not by relaxing this table's RLS write policy itself; the RLS policy governing *reads* of this table remains standard tenant-isolated, while the *write* path for public submission is a narrowly-scoped service-role/application-layer insertion path that sets `company_id` server-side (derived from the referenced `listing_id`, never accepted as public input) so a malicious public submitter cannot spoof a request into a different company's queue. Rate-limiting and basic spam/bot mitigation (e.g., a CAPTCHA or submission-throttling layer) at the API gateway is the recommended Phase 8 hardening for this specific unauthenticated write surface, flagged here since it is the only unauthenticated INSERT path in the entire schema.
- **Soft Delete:** Standard across all three tables — `marketplace_listings`' soft-delete is deliberately narrow in scope (§9.0/§9.1), reserved for genuine data-entry error rather than ordinary end-of-life, which is instead expressed via `status = 'archived'`.
- **Evidentiary/Funnel Value:** `viewing_requests` rows are preserved (soft-delete-only, never hard-deleted in the ordinary case) as real funnel-analytics/lead-conversion product data, per Phase 2's relationship catalog (§2.1.G) explicitly flagging this as a real product asset worth retaining.

## Module 9 (Marketplace) — Architecture Review

- **PostgreSQL Best Practices:** UUIDv7 PKs throughout; `TIMESTAMPTZ` for all point-in-time columns (`submitted_at`, audit columns) versus correctly-typed `DATE` for calendar-date concepts (`published_date`, `expiration_date`, `preferred_viewing_date`) — the identical DATE-vs-TIMESTAMPTZ discipline applied correctly and consistently since Module 5. `NUMERIC(12,3)` paired with an explicit `currency` column on `marketplace_listings`' two monetary fields, matching the Global Convention exactly.
- **Referential Integrity:** Every FK in this module is `NOT NULL` and `RESTRICT`-on-delete for the structural parent-child relationships (`apartment_id`, `building_id`, `listing_id`, `file_id`), except the standard `SET NULL` actor-attribution columns (`created_by`/`updated_by`/`deleted_by`/`uploaded_by`) — consistent with the platform-wide "preserve history, sever only the actor-attribution edge" pattern established in every prior module. Notably, this module introduces **no** nullable structural FK anywhere (unlike, e.g., `maintenance_requests.apartment_id`/`tenant_id`) — every listing has exactly one apartment, every image has exactly one listing, every viewing request has exactly one listing, a direct consequence of this module's narrower, INTERNAL-only scope (§9.0).
- **Constraint Quality:** The two partial-unique "at most one active/flagged row per parent" constraints in this module (`uq_marketplace_listings_one_active_per_apartment`, `uq_listing_images_one_cover`) were both deliberately modeled on this schema's already-validated pattern for the identical shape of business rule (Module 2's active-subscription constraint, Module 4's active-parking-assignment constraint, Module 5's active-lease constraint) rather than reinvented ad hoc — continuing the "solve the same class of problem the same way every time" discipline that keeps this schema predictable.
- **Index Quality:** Every composite index in this module was checked for column-order correctness (equality-before-range/sort, `DESC` embedded where a query needs most-recent-first or featured-first) — no index found with the wrong leading column. One genuine redundancy was identified and explicitly called out rather than silently shipped: `idx_listing_images_listing_display_order` fully overlaps with `uq_listing_images_listing_display_order`'s own backing index and is therefore not actually a separate physical index, documented in place (§9.2) per the same transparency discipline already demonstrated for `idx_role_permissions_role_id`'s removal (Module 3 §3.5). Two indexes were deliberately **not** created and the omission explicitly justified: a `monthly_rent`/`security_deposit` range index on `marketplace_listings` (§9.1) and a standalone `phone_number`/`email` index on `viewing_requests` (§9.3) — both real candidates a less careful pass might add reflexively, both correctly identified as lacking a stated query requirement to justify their write-amplification cost.
- **Query Performance:** Every stated required query shape (Published Listings, Company Listings, Building Listings, Apartment Listings, Public Listing Search, Image Loading, Viewing Request Management, Search, Filtering, Pagination) is explicitly mapped to a specific index in §9.6, with no requirement left unaddressed and no index added without a corresponding named requirement — the same discipline as Modules 4, 6, 7, and 8's requirement-to-index mapping.
- **Security:** Reviewed against every requirement in the module brief (§9.7) — RBAC, audit logging, multi-tenant isolation, and soft delete all confirmed present. This module's one genuinely novel security consideration relative to every prior module — a real public, unauthenticated read surface (`marketplace_listings`/`listing_images`) and a real public, unauthenticated write surface (`viewing_requests` INSERT) — is addressed with an explicitly narrow, deliberately-scoped RLS carve-out and a server-side-only `company_id`-assignment discipline for public writes, rather than a blanket relaxation of tenant isolation; both are flagged as the highest-scrutiny surfaces in the schema for any future column addition.
- **Multi-Tenant Isolation:** Confirmed as intentionally non-standard for `marketplace_listings`/`listing_images` (public-read carve-out) and standard for `viewing_requests` (read side) — the exact, minimal cross-tenant surface this module's product purpose requires, matching (and now physically implementing) the cross-tenant exception Phase 1 §1.24 and Phase 2 §2.4 already flagged conceptually, rather than either over-restricting (breaking the marketplace's actual public-browsing purpose) or under-restricting (exposing lead/applicant data that has no legitimate public-read case).
